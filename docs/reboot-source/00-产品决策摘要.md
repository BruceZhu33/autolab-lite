# AutoLab Lite 产品决策摘要

版本：v1.3  
日期：2026-09-17

## 一句话定义

AutoLab Lite 是个人研究者的 GPU 实验工作台：用户和 GLM 驱动的编码 Agent 决定做什么，系统把确认后的实验计划可靠地排队执行，并保留足够的研究证据用于下一轮判断。

## 产品由三部分组成

1. **高密度科研工作台**：看板、计划确认、运行详情和 GPU 服务器；Multica 源码/品牌是否可用由 M5 许可决策决定。
2. **轻量执行控制面**：Plan、Job、GPU Lease、Runner、日志、指标和恢复。
3. **文件化科研记忆**：研究背景、实验假设、事前成功判据、结论和失败经验。

GLM 驱动的编码 Agent 是首要研究协作者，不是产品内置的一套聊天系统；Runner 是执行器，不做科研决策；UI 是投影，不拥有业务状态。

首个验收组合采用 **GLM Coding Plan + Claude Code Agent 外壳 + AutoLab MCP**。模型是 GLM；Claude Code 只是承载模型和工具调用的宿主。产品不依赖某个 Agent 外壳，MCP/CLI 协议保持可移植。

## 四条不可违反的规则

### 1. 研究语义与运行事实分开

- 项目文件保存：目标、约束、假设、实验设计、成功判据、结论、失败经验。
- SQLite 保存：批准、队列、GPU Lease、派发、进程状态、事件游标、退出码和产物索引。
- Runner 在控制端离线时保存远端进程事实。
- 同一状态不得同时由 Markdown、数据库和前端分别维护。

### 2. 实验先定义，再执行

每个 Plan 在批准前必须说明：

- 本轮假设和相对上一轮的改动；
- baseline、数据集和评价指标；
- 事前成功判据；
- 风险和失败后的处理方式；
- 将展开出的 Job、GPU、并发和超时。

用户批准后，上述执行契约冻结；改变口径必须创建下一版 Plan。

### 3. Agent 不能自行消耗 GPU

Agent 可以读项目、修改代码、创建 DRAFT Plan、请求审批、分析结果和建议下一轮。只有用户在本地 UI/CLI 确认准确 revision 与 spec hash 后才能生成 Job；普通 MCP 不暴露批准入口。停止、重试和高风险操作也必须指向明确资源。

### 4. 失败也是资产

失败 Job 保留原始日志和事实；被否定的实验保留结论、证据和重新考虑条件。产品不通过删除或覆盖历史来制造“成功”。

## P0 只做的闭环

```text
连接 GPU 服务器
→ 登记已有项目
→ GLM Agent 创建实验草案
→ 用户一次确认
→ 展开并排队多个 Job
→ Runner 持续执行
→ 查看日志、指标和产物
→ 记录结论
→ 创建下一版实验
```

## P0 不做

- 不嵌入 RD-Agent。
- 不引入 Any Science Framework 源码或多 Agent 角色系统。
- 不做团队、成员、权限、通知和通用 Issue 系统。
- 不做自动论文检索、自动报告、可信测试集、消融平台或全自动科研。
- 不建立项目科研阶段状态机。
- 不让 Multica 原领域内核重新进入产品。
- 未完成许可决策前，不复制 Multica UI 源码、品牌图标或做像素级复刻。

## 最小事实源

| 内容 | 权威来源 |
|---|---|
| 研究背景、约束 | 项目 `.autolab/context.md` |
| 实验假设、成功判据、结论 | `.autolab/experiments/*.md` |
| 失败经验 | `.autolab/knowledge/failures.md` |
| 已批准执行参数 | Control 中不可变 Plan Revision |
| 队列、GPU、运行和退出码 | Control SQLite |
| 控制端离线期间的进程事实 | Runner |
| 看板列、进度和提醒 | 由上述事实派生，不单独保存 |

## 成功的判断

产品是否成功，不看有多少 Agent、状态或页面，只看研究者能否在真实 GPU 项目上连续完成十轮“提出修改—确认—训练—看结果—再修改”，期间不需要手工修数据库，也不会因为页面、控制端或网络中断而丢失真实任务状态。
