# AutoLab Lite 产品需求 v1.0

- 状态：新工作区开发基线
- 日期：2026-09-17
- 产品形态：单用户、本地控制端、用户自有 GPU 服务器
- 首要原则：先把连续训练迭代做顺，再扩展科研自动化能力

## 1. 产品定义

AutoLab Lite 是一个面向个人研究者的 GPU 实验编排器。

用户主要在 GLM 驱动的编码 Agent 中描述目标、讨论修改和查看总结；AutoLab Lite 不重复实现一个通用 AI 聊天产品，而是通过 MCP/CLI 向 Agent 提供稳定工具，并向用户提供一个轻量控制台，用来确认计划、查看队列、日志、指标和异常。

一句话价值：

> 把“登录服务器、进入项目、按多个数据集排队训练、观察结果、修改后再跑”变成可靠、可恢复、可审计的标准循环。

### 1.1 科研工作区原则

产品同时管理两类不同信息，必须保持边界：

- **研究语义**：目标、约束、假设、实验设计、事前成功判据、结论和失败经验，保存在项目的 `.autolab/` 文件中，可被用户和 Agent 直接阅读、评审和版本控制。
- **运行事实**：计划批准、Job、GPU Lease、派发、事件、日志游标、退出码和产物索引，保存在 Control 数据库中。

Multica 控制台只展示两者的派生视图，不拥有第三套状态。聊天记录不是事实源，Agent 角色也不是产品实体。

## 2. 目标用户和前提

目标用户是拥有一台或多台 Linux GPU 服务器的个人研究者。首版假设：

- 单用户，不需要团队、成员、权限和多租户。
- 服务器可通过 SSH 访问。
- 代码项目可以已经存在于远端服务器；首版不强制把代码复制到本地。
- 用户愿意在真正执行训练前确认一次结构化计划。
- Agent 负责理解自然语言与提出修改；远端项目通过 Control 的受限文件/Git 工具修改，执行系统负责确定性落地。
- 用户仍然是 PI：Agent 可以提案、执行和分析，但不能替用户批准会消耗 GPU 的计划或宣布科研结论成立。
- P0 第一优先适配 GLM Coding Plan；首个验收宿主为 Claude Code，模型仍为 GLM。协议不得依赖 Claude Code 私有状态。

## 3. 产品目标

### 3.1 P0 目标

1. 注册一台 GPU 服务器并验证 SSH、Runner 和 GPU 状态。
2. 登记一个远端代码项目，包括工作目录、环境和默认命令。
3. Agent 根据用户要求创建一个可审查的训练计划版本。
4. 将数据集、seed 或配置矩阵展开为多个 Job 并进入队列。
5. 按指定 GPU 和并发限制可靠调度，避免同一卡重复占用。
6. 实时查看当前任务、日志尾、退出码、耗时、指标和产物。
7. 支持停止、失败重试和基于上一轮结果创建新计划版本。
8. 控制端或网络短暂中断后，能够与服务器 Runner 对账并恢复真实状态。

### 3.2 成功标准

- 完成服务器首次配置后，从用户提出训练要求到任务开始运行不超过 5 分钟。
- 用户可以连续完成至少 10 轮“修改—训练—查看结果”，无需修数据库或理解内部状态码。
- 一个页面冷启动只请求该页面需要的数据，核心页面首屏请求不超过 3 个。
- 页面可交互时间目标小于 1 秒；普通点击反馈小于 200ms。
- 单个任务事件不能引发全站缓存失效或整页重新获取。
- 控制端重启后，运行中任务不重复派发、不丢日志、不虚报停止。

## 4. 非目标

以下内容不进入 P0，也不能作为 P0 架构前置条件：

- 团队协作、Workspace、成员、邀请、角色和权限系统。
- 通用团队协作 Issue 系统、复杂筛选、Gantt、Swimlane、Presence 或通知中心。保留高密度横向科研任务板和卡片体验，但改用 AutoLab Lite 的轻量数据模型。
- 内置通用 AI 聊天、Agent 人设、评论线程和社交式时间线。
- 云托管、计费、额度购买、组织管理。
- 全自动论文检索、报告生成、消融矩阵、多 seed 科研结论自动发布。
- 受保护 test 一次性释放、三执行身份隔离和完整可信评测平台。
- 为所有未来异常建立数据库级有限状态机和 trigger。
- Scholar、Methodologist、Executor、Analyst、Reviewer 等常驻角色和多 Agent 编排系统。
- 用 Markdown 卡片状态驱动调度，或在数据库、文件和前端重复保存同一运行状态。
- 同时支持 macOS、Windows、Linux 桌面打包；P0 先跑通当前开发机和 Linux Runner。

这些能力以后只能在真实使用证明需要时，以可插拔策略加入。

## 5. 核心用户流程

### 5.1 首次设置

1. 用户输入服务器名称、SSH 地址、端口和用户名。
2. 系统使用系统钥匙串或受限凭据文件保存认证信息。
3. 系统探测 Python、GPU、磁盘和已有 Runner。
4. 若 Runner 缺失，用户确认后部署；若版本不一致，可升级。
5. 服务器进入 READY，显示 GPU 型号、显存和当前占用。

### 5.2 登记项目

1. 用户选择服务器和远端项目目录。
2. 系统验证目录存在、可读，并获取 Git commit、branch 和 dirty 状态。
3. 用户登记运行环境：conda 环境、venv 路径或命令前缀。
4. 用户可登记默认训练命令、输出目录和指标文件规则。
5. 项目保存后即可创建计划，不经过项目阶段状态机。

### 5.3 创建并确认训练计划

用户在 GLM Agent 中提出例如：

> 在项目 A 上把 lr 改成 1e-4，依次跑 dataset-x、dataset-y，每个 3 个 seed，用 0、1 号卡，一次最多两个任务。

Agent 调用产品工具创建 DRAFT Plan Revision。控制台或工具返回以下预览：

- 研究假设和相对上一版的变化。
- baseline、评价指标和事前成功判据。
- 风险、失败后的处理方式和需要保留的证据。
- 代码版本和修改摘要。
- 工作目录与环境。
- 命令模板。
- 数据集、seed 和其他变量矩阵。
- 展开后的 Job 数量。
- GPU 选择、并发数、超时和预估资源。
- 输出目录、指标和产物规则。

用户在本地 UI/CLI 中确认准确的 Plan revision 和 spec hash 后，Plan 变为 APPROVED，系统以幂等方式生成 Job。一次确认覆盖整批计划，不要求逐任务批准。普通 Agent MCP 工具只能请求审批和查询结果，不能直接执行人类批准操作。

### 5.4 队列和执行

1. Job 进入 QUEUED。
2. 调度器为 Job 获取持久化 GPU Lease。
3. 控制端向 Runner 发送带 `dispatch_id` 的不可变 Manifest。
4. Runner 对同一 `dispatch_id` 幂等处理，启动独立进程组并写本地事件和日志。
5. 控制端消费事件，更新 Job 投影并向客户端发送精确事件。
6. Job 结束后释放 GPU Lease，登记退出码、耗时、指标和产物。

### 5.5 修改和下一轮

1. Agent读取上一版 Plan、Job 结果和日志摘要。
2. 用户提出修改。
3. Agent创建新的 Plan Revision，明确相对上一版的差异。
4. 用户确认后生成新 Job。

历史计划与任务不可静默修改。所谓“回到迭代阶段”不存在；只是创建下一版计划。

### 5.6 沉淀研究资产

1. 项目首次登记后，可创建 `.autolab/context.md`，记录研究目标、资源限制、评价规则和不可违反的约束。
2. 每个 Plan Revision 对应一份实验记录 `.autolab/experiments/EXP-xxxx.md`，记录假设、改动、baseline、指标、事前成功判据、风险和结论。
3. Plan 批准时保存实验记录的内容 hash；批准后修改实验设计必须创建新 revision，不能改变已经执行实验的口径。
4. Job 结束后，Agent 或用户把结论和证据链接写回实验记录。运行状态仍以数据库为准，实验记录不保存 QUEUED/RUNNING 等调度状态。
5. 被否定或停止投入的方向写入 `.autolab/knowledge/failures.md`，至少包含失败原因、证据和重新考虑条件。
6. Control 可以读取和校验这些文件，但不得根据自然语言猜测运行状态。

## 6. 功能需求

### FR-1 服务器管理

- 新增、编辑、停用服务器。
- SSH 连通性测试。
- GPU、显存、利用率、温度和磁盘探测。
- Runner 探活、部署和升级。
- 对已有任务历史的服务器只允许停用，不做级联删除。

### FR-2 项目管理

- 项目至少包含：名称、server_id、remote_workdir、环境配置、默认命令、输出根目录。
- 展示 Git revision、branch、dirty 状态；非 Git 项目也可运行，但必须显示“无版本锚”。
- 项目没有科研阶段，只允许 active/archived。

### FR-3 计划版本

- Plan Revision 创建后保存结构化 JSON，不直接执行自然语言。
- 必填字段：项目、实验记录引用与 hash、假设、相对改动、baseline、指标、事前成功判据、代码锚、命令、变量矩阵、资源、超时、输出规则。
- 计划确认前展示完整展开结果。
- APPROVED 后不可修改；修改必须生成新 revision。
- 成功判据随 APPROVED Plan 冻结，结果出来后不得为迎合结果修改本轮判据。
- 对同一个 approval idempotency key 重试不得重复生成 Job。

### FR-4 队列与调度

- 支持数据集、seed 和任意键值参数的笛卡尔积或显式任务列表。
- 支持指定服务器、GPU 集合、每 GPU 并发和全局并发。
- GPU Lease 必须持久化；控制端崩溃后可以重建。
- 首版使用单控制端 FIFO，并允许用户调整 QUEUED Job 顺序。
- 失败 Job 不自动无限重试；默认由用户或 Agent 显式重试。

### FR-5 远端执行

- Runner 必须校验非空 token、Manifest 版本、dispatch_id 和 HMAC；只有显式 test mode 可以关闭 HMAC。
- 每个 Job 使用独立进程组、日志文件和输出目录。
- Runner 保存足够状态，使控制端断开后任务仍可完成。
- 停止采用 TERM → grace period → KILL，并回报最终事实。
- Runner 不解释科研语义，只执行已确认 Manifest。
- Runner 不拥有等待队列或 GPU 分配权；它只执行 Control 已持有全部 Lease 的 Job。
- Runner 对 workdir/output 做允许根和 symlink containment 校验，并安全识别持久化进程身份。

### FR-6 日志、指标和产物

- 运行中支持日志尾和按游标增量获取，不反复传输完整日志。
- 终态保存退出码、开始/结束时间、失败摘要。
- P0 指标来源为声明的 JSON/CSV 文件或日志正则；必须注明来源，不用于自动科研结论。
- 产物登记至少包含路径、大小、hash 和类型。
- 控制台只默认展示摘要，原始日志和文件按需打开。

### FR-7 停止、重试与恢复

- QUEUED Job 可直接取消。
- RUNNING Job 可请求停止，界面区分“停止请求已发出”和“已确认停止”。
- 重试创建新 Job，记录 `retry_of_job_id`，不覆盖旧 Job。
- 控制端启动时向全部 READY Runner 对账活跃任务。
- Runner 不可达时派生 `observation_state=UNKNOWN`，不改变 Job 执行状态，也不把任务伪装为失败或已停止。

### FR-8 GLM Agent / MCP / CLI 接口

P0 先提供 CLI 和本地 API，M4 将同一工具面暴露为本地 stdio MCP server。至少包括：

- `list_servers`
- `probe_server`
- `list_projects`
- `inspect_project`
- `list_project_files`
- `read_project_file`
- `apply_project_patch`
- `get_git_status`
- `get_git_diff`
- `create_plan_revision`
- `preview_plan`
- `request_plan_approval`
- `get_plan_approval_status`
- `list_jobs`
- `get_job`
- `tail_job_log`
- `cancel_job`
- `retry_job`
- `get_run_results`

读操作可直接执行。`apply_project_patch` 必须限制在登记项目根、返回 diff 并使用 expected hash 防止覆盖并发修改。会产生计算资源消耗的动作必须通过 APPROVED Plan；`approve_plan`、删除凭据、强制停止和覆盖产物是 owner-scope 的本地 UI/交互式 CLI 操作，不作为普通 MCP 工具暴露。MCP 进程只获得 agent-scope capability，owner 凭据不得进入其环境或配置。

GLM 优先适配要求：

- 工具名称、参数和返回结构针对 GLM 工具调用做人工实测，描述短小、明确、无隐含上下文。
- MCP 返回默认提供摘要与资源 ID；原始日志、完整 Plan 和 Artifact 按需读取，避免一次调用灌入大量上下文。
- GLM API Key 和 Coding Plan 配置由 Agent 宿主管理，不进入 AutoLab 设置、数据库或日志。
- 首个验收组合为 GLM Coding Plan + Claude Code Agent 外壳；随后用同一 MCP 对另一个 GLM 宿主做兼容验证。
- AutoLab 不直接调用 GLM API。以后若增加无人值守 Planner，必须作为可选模块单独评审。
- 默认由 Control 通过 SSH/SFTP 访问远端项目，GLM 不需要维护长期 SSH 会话；MCP 不提供无限制远端 shell。

### FR-9 高密度科研薄控制台

P0 保留用户已经验证喜欢的体验：左侧导航、顶部页面结构、横向实验看板、紧凑圆角卡片、工作区详情布局，以及 GPU 服务器页面的信息表达。

这是一项正式产品需求，而不是临时参考。Multica 源码和品牌能否用于实现取决于 M5 许可决策；独立实现路径保留信息层级和主要交互目标，不要求像素级复刻。所有路径都不得恢复 Workspace/Issue 查询系统。

P0 只实现四个业务页面：

1. Board：高密度横向看板，以项目/实验卡片展示当前工作态。
2. Plan Workspace：计划差异、展开任务和一次确认。
3. Run Detail：队列、GPU 占用、日志、指标和停止/重试。
4. GPU Servers：SSH、Runner、GPU 与磁盘，保留现有页面的卡片式表达。

看板列是轻量派生视图，推荐为“待计划、已排队、运行中、需要你、最近完成”。卡片位置根据 Plan/Job 实况计算，不作为新的项目权威状态机。卡片默认回答：项目是什么、最新计划、Job 进度、使用哪张 GPU、最新指标以及是否需要用户处理。

### FR-10 科研资产与记忆

- 项目可初始化最小 `.autolab/` 目录，但不得要求把训练代码迁入新的专用工作区。
- `context.md`、实验记录和失败知识使用简单、可人工编辑的 Markdown；机器必需字段通过短小 front matter 或关联的 Plan JSON 表达。
- Agent 开始新一轮前应读取项目 context、上一轮实验记录和相关失败经验，避免只依赖当前对话。
- 结果分析必须引用具体 Job、指标文件或 Artifact，不允许只写“效果更好”。
- P0 不建立全文知识库、向量数据库、RAG 管线或知识图谱；文件搜索已经足够。
- UI 只按需显示研究摘要，不为文件再维护一份可编辑副本。

## 7. 状态模型

### 7.1 Project

```text
ACTIVE | ARCHIVED
```

### 7.2 Plan Revision

```text
DRAFT → APPROVED
DRAFT → ABANDONED
```

APPROVED 不回退；新修改创建下一 revision。

### 7.3 Job 内部状态

```text
QUEUED
DISPATCHING
RUNNING
SUCCEEDED
FAILED
CANCELLING
CANCELLED
TIMED_OUT
```

UI 可归并为：排队中、运行中、成功、失败、状态未知。

### 7.4 Runner 观察状态

```text
CONFIRMED | STALE | UNKNOWN
```

观察状态是由最近 Runner 联系、事件游标和 snapshot 派生的连接事实，不是 Job 执行状态。Runner 不可达时，RUNNING/DISPATCHING 等非终态 Job 保持原执行状态并显示 `UNKNOWN`；恢复连接后根据远端事实继续 RUNNING 或进入真实终态。不得把 `LOST` 保存成不可恢复的 Job 终态。

项目进度、实验轮次和计划完成率全部由 Plan/Job 派生，不另存权威状态。

实验文件中的结论和 `iterate/promote/stop` 决定是科研记录，不参与调度状态迁移。

## 8. 非功能需求

### NFR-1 性能

- 核心页面首屏 HTTP 请求数不超过 3。
- WebSocket/SSE 事件必须包含资源类型与资源 ID，只更新相关缓存。
- 禁止无参数全局缓存失效。
- 建立实时连接后不再进行 5 秒轮询；断线时才使用退避轮询。
- 1000 个历史 Job 下，项目页和队列页仍在 1 秒内返回首屏摘要。

### NFR-2 可靠性

- 所有派发、批准、取消和重试写操作支持幂等键。
- Runner 事件使用单调序号；重复事件不重复产生副作用。
- 控制端数据库使用 SQLite WAL；事务只覆盖本地短写，不在事务中等待网络。
- 网络中断、控制端崩溃和 Runner 重启都有明确对账行为。

### NFR-3 安全

- 控制端只监听 loopback，并区分 agent/owner capability scope；MCP 只获得 agent scope。
- SSH 密钥和 Runner token 不进入普通数据库导出、日志或前端响应。
- 首次 SSH 连接展示并确认主机指纹，后续固定该指纹；禁止关闭 host key 校验。
- 命令只在登记的项目工作目录下执行，输出目录必须位于配置根目录内。
- 删除、强制停止和覆盖产物必须有明确目标，禁止基于未解析变量或宽泛路径执行。

### NFR-4 可维护性

- P0 生产源码目标小于 20,000 行，不包含生成文件和测试。
- 前端保留高密度 Shell、看板和卡片的产品体验；仅在许可路径允许时使用 Multica token/primitives，任何路径都不引入其通用协作领域内核。
- 一个页面只依赖对应领域 API；不得用 fetch 拦截层模拟另一套产品协议。
- 数据库迁移只为已经实现的用户流程服务。

## 9. P0 验收场景

1. 本地 Runner：创建 3 个短任务，按并发 1 依次成功，日志和产物可见。
2. 真实 SSH：在指定远端项目目录运行一个训练命令并带回指标。
3. 多数据集：2 个数据集 × 3 个 seed 展开为 6 个 Job，Job 参数准确。
4. GPU 互斥：同一卡并发限制为 1 时不会重复派发。
5. 幂等：批准请求重复 3 次，只生成一批 Job；派发重试不重复启动进程。
6. 停止：运行中任务完成 TERM/KILL 链，最终状态与远端事实一致。
7. 控制端重启：任务继续运行；重启后自动恢复 RUNNING 并继续收事件。
8. Runner 不可达：任务观察状态显示 UNKNOWN，不修改其执行状态，不误报 FAILED 或 CANCELLED。
9. 下一轮：基于第一次结果创建 revision 2，旧计划和旧结果保持不变。
10. 性能：训练事件到达时只更新相关 Job，不触发 Projects、Servers 等无关查询。
11. 研究资产：新会话只读取项目 `.autolab/` 文件和产品 API，即可说明上一轮做了什么、成功判据是什么、结果证据在哪里以及为什么继续或停止。
12. GLM Agent：GLM 能通过 MCP 完成“读取/修改远端项目与上一轮结果→创建 DRAFT Plan→请求并等待用户在本地 UI/CLI 批准→追踪 Job→记录证据化结论”，期间不需要模型直接 SSH 维持训练任务，也不能自行调用批准入口。

## 10. 后续能力进入条件

只有 P0 在真实项目上完成不少于 10 轮连续迭代后，才评估：

- 自动失败诊断与修复建议。
- 基线比较、候选选择和多 seed 汇总。
- 可信评测和测试集隔离。
- 消融矩阵。
- 自动报告。
- 多服务器智能调度。

每项能力都必须先写清楚真实用户决策，再决定是否需要新实体或状态；不得先扩状态机再寻找使用场景。
