# 目标架构与数据模型

## 1. 系统边界

```text
用户
  │ 自然语言、确认、查看结果
  ▼
GLM 驱动的编码 Agent
  ├── 本地 stdio MCP：项目文件、Git、研究记录、计划与任务工具
  └── 只能创建 DRAFT/请求审批；不能替用户批准 GPU 消耗
  ▼
Control（用户电脑）
  ├── SQLite：项目、计划、队列、事件投影
  ├── Scheduler：FIFO、并发与 GPU Lease
  ├── Reconciler：控制端重启/断线对账
  ├── SSH Transport：部署、探测与端口隧道
  └── Event Gateway：向薄控制台发送精确更新
          │ SSH 隧道或受限网络
          ▼
Runner（Linux GPU 服务器）
  ├── 幂等接收 Manifest
  ├── 启动/停止独立进程组
  ├── 持久化任务状态和事件序号
  └── 保存日志与输出目录
```

Agent 是规划层，项目文件是研究记忆，Control 是控制面，Runner 是执行面。四者不得互相替代：

- Agent 不直接用临时 SSH 会话承担长期任务状态。
- Agent 不获得无限制远端 shell；远端代码和 `.autolab/` 通过 Control 的项目根受限工具读写。
- 项目文件不保存 QUEUED、RUNNING、GPU Lease 或进程存活等运行状态。
- Control 不自行解释自然语言或推断科研结论。
- Runner 不决定下一轮实验，也不修改计划。
- 人类批准由本地 UI/CLI 完成；普通 MCP 工具不能伪造用户确认。

## 1.1 事实源边界

| 领域 | 权威来源 | 说明 |
|---|---|---|
| 研究目标、约束、假设、结论 | 项目 `.autolab/` 文件 | 人和 Agent 可读，可进入 Git |
| 批准后的执行契约 | `plan_revisions.spec_json` | 批准后不可变，包含实验记录 hash |
| 队列、GPU Lease、事件和退出码 | Control SQLite | 原子写入和查询投影 |
| 控制端离线期间的进程事实 | Runner 本地状态 | 恢复后由 Control 对账 |
| 看板列、进度、提醒 | 派生 ViewModel | 不单独成为状态机 |

研究文件和数据库可以互相引用，但不能分别维护同一状态。Control 可以缓存研究文件摘要用于页面查询，缓存必须能从文件重建。

## 2. 建议组件

### 2.1 Control

推荐继续使用 Python 3.12、FastAPI、SQLite/WAL、asyncssh 和 httpx。Control 提供：

- loopback HTTP API；
- Agent/CLI 工具调用；
- 轻量前端所需查询；
- Scheduler、Dispatcher、Monitor/Reconciler 后台任务；
- 精确的 WebSocket 或 SSE 事件。

后台任务与 API 可以先在同一进程内，但模块边界要独立。P0 不引入 Redis、Celery、PostgreSQL或消息队列。

### 2.2 Runner

Runner 根据 v1 协议从零实现最小 FastAPI 进程；当前 gpu-agent 只作为 reference：

- 服务器端依赖少；
- 任务在控制端离线后继续运行；
- dispatch_id 幂等；
- 事件序号、日志尾和停止链可恢复；
- 不连接外部数据库。
- 不维护等待队列或第二套 GPU 调度权；GPU 已占用时明确拒绝，由 Control 处理。
- 非 test mode 下 Token/HMAC 缺失时拒绝启动；工作目录和输出目录必须通过本机允许根校验。
- 使用 argv 和 `shell=False`；需要 shell 时必须在已批准 Manifest 中显式出现 `bash -lc`。
- 重启后使用 PID + process start time + Runner nonce 等身份核验进程，禁止只凭旧 PID 发信号。

### 2.3 Web：保留用户体验，替换领域内核

Web 是 Control 的一个薄客户端，并保留当前界面中用户喜欢的信息密度和交互目标。Multica 源码、品牌和具体组件能否使用由 M5 许可决策决定；独立实现路径不得读取或复制源码快照。

产品体验要求：

- design tokens、字体层级、间距、圆角、阴影和颜色；
- Sidebar、PageHeader、Dashboard shell；
- 横向 Kanban/Issue 看板布局；
- Board card、column、拖拽反馈和横向滚动体验；
- 项目工作区的主从布局；
- GPU Servers 页面及其遥测卡片。

重写：

- `Issue`/`Workspace`/`Member`/`Agent` 等领域类型；
- IssueSurface 的多模式查询规划、facet、status branch 和分页体系；
- auth、billing、presence、notification、inbox 等 Provider；
- fixture fetch 拦截、Multica API client 和旧 realtime 客户端；
- 任意事件触发的全局 query invalidation。

可以使用 Next.js/React，但必须满足：

- 不引入通用 issue/workspace/domain core；看板直接消费 AutoLab `BoardCardView[]`；
- 每个页面直接调用自己的资源 API；
- 只存在一套数据模型；
- 不使用 fetch monkey patch 或 fixture/real 双协议分流；
- fixture 只能是 API client 的测试实现，不能在生产运行时截获全局 fetch。

### 2.4 Agent Client

优先提供一组窄工具，而不是内置聊天窗口。适配顺序为：

1. `autolab` CLI：人工诊断、自动化测试和 M0/M1 开发入口；
2. 本地 stdio MCP server：GLM Agent 的首要产品入口；
3. Python/TypeScript client：只在实际调用者需要时增加；
4. JSON Schema：约束 Plan、Manifest 和 MCP 结构化返回。

第一优先模型是 GLM Coding Plan 中的 GLM 编码模型。首个验收组合是 GLM Coding Plan + Claude Code Agent 外壳；Claude Code 只是 GLM 与 MCP 的宿主，不是产品的模型依赖。MCP 工具不得读取宿主私有会话状态，也不得包含 `claude_*` 或 `codex_*` 等厂商字段。

AutoLab 不配置或转发模型 API。GLM API Key、Base URL、模型选择和配额由 Agent 宿主管理，因此 Control 仍然没有 LLM Provider、聊天记录或 token 账本。

Control 至少区分 `agent` 与 `owner` capability scope。MCP 子进程只获得 agent scope，不能调用批准、凭据删除、强制停止或覆盖产物等 owner 接口；owner 凭据保存在系统钥匙串或本地 App 进程内，不写入 MCP 配置、环境或日志。普通 MCP 工具不暴露 `approve_plan`。Agent 调用 `request_plan_approval` 后只能轮询审批状态；用户必须在本地 UI 或交互式 TTY CLI 中确认准确的 `plan_revision_id + spec_hash`。CLI 不允许非交互 stdin 静默批准；需要输入短 hash 或通过系统确认。若未来宿主支持可信人机确认回调，可增加绑定 revision、hash 和过期时间的一次性 approval receipt 适配器，不能仅依赖提示词。

### 2.4.1 远端项目工作区

首要拓扑是：Agent 在用户工作站运行，通过本地 stdio MCP 调用 Control；Control 通过 SSH/SFTP 操作登记的远端项目根。M4 至少提供：

- `list_project_files`、`read_project_file`；
- `apply_project_patch`，带 expected content hash 和 patch preview；
- `get_git_status`、`get_git_diff`；
- 专用 research context/experiment/failure 工具。

所有路径必须是项目根下的相对路径，解析 `realpath` 后再次校验 containment；拒绝绝对路径、`..` 和越界 symlink。不提供无限制通用 shell MCP 工具，不自动 commit、push 或覆盖并发修改。

### 2.5 Research Workspace Protocol

在用户已有代码仓库中只增加一个可选的轻量目录：

```text
.autolab/
├── context.md
├── experiments/
│   ├── EXP-0001.md
│   └── EXP-0002.md
└── knowledge/
    └── failures.md
```

`context.md` 记录长期稳定的研究背景、资源条件、指标定义和红线。每个实验记录至少包含：

```text
id / title / created_at
hypothesis
change_from_previous
baseline
datasets_and_metrics
success_criteria
risk_and_fallback
plan_revision_id
evidence              # Job / Artifact / metrics 引用
conclusion            # pending | supported | rejected | inconclusive
next_decision         # iterate | promote | stop，可选科研决定
```

这里的 `conclusion` 和 `next_decision` 是研究记录，不驱动 Scheduler。实验执行状态只能从 Plan/Job 查询。

P0 只提供初始化、读取、校验和记录结论所需的窄工具。不做角色编排、向量数据库、自动领域建模或 Markdown 状态机。

## 3. 最小数据模型

P0 建议从 7 张业务表开始。`schema_migrations` 等基础设施表不计入。

### 3.1 servers

```text
id
name
transport_mode       # local | ssh
host
port
username
credential_ref
host_key_fingerprint
runner_port
runner_token_ref
runner_version
status_hint
allowed_work_roots_json
allowed_output_roots_json
last_seen_at
created_at
updated_at
```

GPU 遥测不需要为每个采样永久落表；最近一次快照可以保存 JSON，历史遥测后置。

### 3.2 projects

```text
id
name
server_id
remote_workdir
environment_json
default_command
output_root
metric_rules_json
status               # ACTIVE | ARCHIVED
created_at
updated_at
```

项目不保存科研阶段。

### 3.3 plan_revisions

```text
id
project_id
revision_no
parent_id
status               # DRAFT | APPROVED | ABANDONED
code_anchor_json
spec_json
spec_hash
summary
experiment_ref        # .autolab/experiments/EXP-xxxx.md
experiment_hash       # 批准时内容 hash
approved_at
approval_key
approved_by          # local_ui | local_cli | trusted_host_receipt
approval_requested_at
created_at
```

`spec_json` 遵循 `PlanSpecV1`，包含 hypothesis、change_from_previous、baseline、metrics、success_criteria、command_template、job_definition、resources、timeout_seconds 和 outputs。APPROVED 后禁止原地修改。

### 3.4 jobs

```text
id
plan_revision_id
ordinal
params_json
dispatch_id
server_id
gpu_indices_json
status
retry_of_job_id
remote_job_id
exit_code
failure_summary
last_runner_event_seq
last_observed_at
queued_at
started_at
finished_at
updated_at
```

同一 Plan 的 `(ordinal)` 唯一；`dispatch_id` 全局唯一。

Job `status` 只允许：`QUEUED | DISPATCHING | RUNNING | CANCELLING | SUCCEEDED | FAILED | CANCELLED | TIMED_OUT`。终态为最后四项。`LOST` 不写入该字段；UI 的 `CONFIRMED | STALE | UNKNOWN` observation state 由 `last_observed_at`、服务器联系时间和对账结果派生。

### 3.5 gpu_leases

```text
id
server_id
gpu_index
job_id
status               # HELD | RELEASING | RELEASED
acquired_at
released_at
```

活跃 Lease 对 `(server_id, gpu_index)` 建唯一约束。它是并发正确性的核心，不依赖页面或内存锁。多 GPU Job 在同一个 `BEGIN IMMEDIATE` 事务中获取全部所需 Lease；任一 GPU 不可用则全部不获取，禁止部分持有后等待。

### 3.6 job_events

```text
id
job_id
runner_instance_id
event_seq
event_type
payload_json
occurred_at
received_at
```

`(runner_instance_id, event_seq)` 唯一。Job 当前状态是事件的快速投影，原始事件用于恢复和诊断。

### 3.7 artifacts

```text
id
job_id
kind
location_kind        # remote | cached | remote_and_cached
remote_path
local_cache_path
sha256
size_bytes
metadata_json
created_at
```

指标可以先放在 artifact metadata 或 Job summary 中。只有出现独立查询需求时才增加 metrics 表。

## 4. 事务边界

P0 只需要少数明确事务：

1. `approve_plan`：仅 owner scope 可调用；校验用户确认的 spec_hash，DRAFT→APPROVED，并按 spec_hash 幂等生成 Job。
2. `acquire_lease`：选取 QUEUED Job、获取全部 GPU Lease、进入 DISPATCHING。
3. `confirm_dispatch`：保存 remote_job_id，进入 RUNNING。
4. `ingest_event`：去重事件，更新 Job 投影；终态时释放 Lease。
5. `request_cancel`：M2 中 QUEUED 直接 CANCELLED；运行中进入 CANCELLING 并产生停止指令。
6. `reconcile`：以 Runner 快照纠正本地非终态，但绝不从终态回退；Runner 不可达只改变派生 observation state，不把 Job 写成 LOST 终态。

网络 I/O 不进入 SQLite 事务。M1 以 `jobs.dispatch_id + DISPATCHING` 作为持久派发意图，网络超时后使用同一 dispatch_id 对账/重放，不新增 outbox。只有后续真实恢复测试证明无法用 Job 行表达时，才通过决策记录评审额外 commands 表，不能预先恢复旧 outbox 全套模型。

科研文件写入不和队列事务混在一起。`approve_plan` 只校验并冻结当时的 `experiment_hash`；批准后文件被修改时，UI 显示“记录已变化”，但不得静默改变已经批准的执行参数。

## 5. Manifest v1

新 Manifest 的规范文件是 `source-assets/contracts-v1/manifest-v1.schema.json`。下面仅为可读示例；命令必须是 argv，Runner 以项目 workdir 为 cwd：

```json
{
  "schema_version": 1,
  "dispatch_id": "dispatch-...",
  "job_id": "job-...",
  "plan_revision_id": "planrev-...",
  "project": {
    "project_id": "project-...",
    "workdir": "/srv/project",
    "code_anchor": {"git_commit": "...", "dirty_patch_sha256": null}
  },
  "execution": {
    "argv": ["python", "train.py", "--dataset", "ds1", "--seed", "1"],
    "environment": {"prepend_path": ["/opt/conda/envs/torch/bin"]},
    "gpu_indices": [0],
    "timeout_seconds": 14400
  },
  "outputs": {
    "root": "/srv/autolab-output/job-...",
    "artifacts": ["**/*.ckpt", "metrics.json"],
    "metrics": [{"kind": "json", "path": "metrics.json"}]
  },
  "created_at": "2026-09-17T10:00:00Z"
}
```

不要把项目阶段、候选、评审、batch、科研结论或 UI 字段放入 Manifest。

## 6. API 形状

### 6.1 查询

```text
GET /api/overview
GET /api/servers
GET /api/servers/{id}/probe
GET /api/projects
GET /api/projects/{id}
GET /api/projects/{id}/research-context
GET /api/projects/{id}/experiments
GET /api/projects/{id}/files?path=
GET /api/projects/{id}/file?path=
GET /api/projects/{id}/git/status
GET /api/projects/{id}/git/diff
GET /api/projects/{id}/plans
GET /api/plans/{id}
GET /api/jobs?project_id=&status=
GET /api/jobs/{id}
GET /api/jobs/{id}/logs?cursor=
GET /api/jobs/{id}/artifacts
```

`/api/overview` 一次返回首页需要的运行中、排队、失败和服务器摘要，避免首页拼接十几个领域查询。

### 6.2 写入

```text
POST /api/servers
POST /api/servers/{id}/runner/install
POST /api/projects
POST /api/projects/{id}/research/init
POST /api/projects/{id}/experiments
POST /api/projects/{id}/patch
POST /api/projects/{id}/plans
POST /api/agent/plans/{id}/approval-requests
POST /api/owner/plans/{id}/approve
POST /api/jobs/{id}/cancel
POST /api/jobs/{id}/retry
```

人类本地 UI/CLI 使用 owner-scope 入口批准准确 `spec_hash`；该入口不注册为普通 MCP tool。Agent 使用 agent-scope `approval-requests` 创建待确认请求并读取结果。

所有写入支持 `Idempotency-Key`。写入成功后返回受影响资源的最新快照。

### 6.3 事件

事件示例：

```json
{
  "type": "job.updated",
  "resource": {"type": "job", "id": "job-1", "project_id": "proj-1"},
  "revision": 17,
  "changed": ["status", "started_at"],
  "occurred_at": "2026-09-17T10:00:00Z"
}
```

前端只更新 `job-1`、相关队列摘要和 `proj-1` 的派生摘要。禁止用任意事件触发所有查询失效。

## 7. 性能预算

- Web 生产包优先按路由拆分；Shell 和看板必须是 AutoLab 轻组件。只有许可决策允许时才可使用 Multica 派生代码；核心控制台不加载 Mermaid、富文本编辑器、Gantt、图表库或多语言营销页。
- Overview 首屏：1 个业务请求。
- Plan 页面：Plan + Job preview 最多 2 个请求。
- Job 页面：详情 1 个请求，日志按游标增量获取，事件连接 1 条。
- SQLite 所有高频条件均有索引：Job status、project_id、plan_revision_id、event runner sequence。
- 事件处理去抖只能合并同一资源，不合并成全局刷新。

## 8. 可扩展点

后续科研能力应作为 Plan Validator、Metric Adapter、Result Policy 或 Report Generator 插件加入，而不是扩大 Project 状态机。例如：

- 多 seed 汇总 = Result Policy；
- 基线对比 = Plan 之间的结果查询；
- 可信评测 = 特殊 Job profile + Validator；
- 消融实验 = Plan matrix builder；
- 自动报告 = 读取历史 Plan/Job/Artifact 的纯派生任务。
- 自主研究策略 = 可选 Planner，只能提交 DRAFT Plan，不能拥有调度和数据库主权。

这样即使某项高级能力失败，基本队列和训练循环仍然可用。
