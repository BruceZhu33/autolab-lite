# 迁移与迭代计划

## 总体策略

新工作区从空仓库开始。旧工程不做原地瘦身，也不先迁移数据库。顺序是：冻结科研资产与执行协议 → 从零实现安全 Runner → Control 纵切 → 真实服务器与受限远端工作区 → Agent 工具 → 许可合规的薄控制台 → 真实使用验证。

每个里程碑必须产生一个用户可观察的真实闭环，不能只以类型检查、契约测试或页面截图作为完成标准。

## M0：新仓库和边界冻结

目标：建立不会重新吸入旧复杂度的骨架。

工作：

- 创建新 Git 仓库和 README。
- 把本交接包复制到 `docs/reboot-source/`。
- 建立 `control`、`runner`、`web`、`protocol` 和 `tests` 目录。
- 写最小 Research Workspace Protocol，生成 `.autolab/context.md`、实验记录模板和失败经验文件。
- 导入并测试 `source-assets/contracts-v1/` 的 Plan、Manifest、Runner Event、Artifact JSON Schema。
- 建立“非目标”和源码行数预算检查。
- 配置只允许 loopback 的 Control 启动方式。

通过门：

- 新仓库不依赖旧 workspace package。
- 全部 P0 业务表不超过 7 张；新增表必须写用户动作依据。
- 能用样例 Plan 展开确定的 Job 列表。
- Plan 批准时能冻结实验记录 hash，研究文件不包含任何队列或运行状态。

## M1：本地双进程执行纵切

目标：在没有前端的情况下跑通最硬链路。

工作：

- 参考旧 gpu-agent，从 v1 协议和测试出发实现新 Runner；禁止复制旧 `/attempts`、内部队列和旧状态。
- Control 实现 servers、projects、plan_revisions、jobs、gpu_leases、job_events、artifacts。
- 实现 local transport。
- 实现 approve_plan、Scheduler、Dispatcher、Runner event ingest。
- 提供 CLI 创建项目、计划、批准、查看任务和日志。
- 重写 `e2e_local`。

真实演示：

```text
创建本地项目
→ 初始化 `.autolab/`
→ 创建带事前成功判据的实验记录和 Plan
→ 提交 3 个 Job，并发限制 1
→ 依次运行
→ 实时日志
→ 全部成功
→ 结果和产物入库
```

通过门：M1 测试连续运行 20 次无重复派发、无 Lease 泄漏。

附加安全门：空 Token/HMAC 启动失败；并发重放只启动一个进程；路径越界和陈旧 PID 测试通过；Runner 不维护等待队列。

## M2：停止、重试和恢复

目标：产品开始具备长期运行可靠性。

工作：

- QUEUED 取消。
- RUNNING TERM→KILL 停止链。
- 显式 retry 新建 Job。
- Control 启动 reconcile。
- Runner 快照和游标过期恢复。
- Job 执行状态与 `CONFIRMED/STALE/UNKNOWN` 观察状态分离。

真实演示：

- 训练中杀掉 Control，任务继续；重启后恢复 RUNNING 并接续日志。
- 发送停止后断网；恢复后以 Runner 事实确认最终状态。
- 重放批准和派发请求不产生重复任务。

通过门：所有不确定状态都显示为不确定，不虚报成功、失败或停止。

## M3：SSH 和真实 GPU

目标：在用户真实服务器和现有项目中完成第一轮训练。

工作：

- 参考 SSH transport、Keychain 和 Runner deploy 重写必要逻辑；不得复制 `known_hosts=None`、Token shell 拼接或宽泛 `pkill -f`。
- 注册真实服务器。
- 首次连接展示并确认主机指纹，后续固定指纹。
- 支持远端已有工作目录和 conda 环境。
- 提供受限远端项目文件/Git 原语，供后续 MCP 复用；不提供无限制通用 shell。
- GPU 探测与持久 Lease。
- 远端输出目录、日志和产物回收。

真实演示：

```text
注册服务器
→ 登记已有项目路径
→ 选择 conda 环境
→ 运行一个真实训练命令
→ 获取指标和 checkpoint
```

通过门：无需手工登录服务器修复产品状态；失败时用户能从错误信息找到真实命令和日志。

## M4：GLM Agent 与 MCP 工具接口

目标：恢复最初的交互方式——用户主要与 GLM 驱动的编码 Agent 对话。

工作：

- 把已经通过 CLI/E2E 验证的 FR-8 工具暴露为本地 stdio MCP server。
- 实现读取研究 context、创建实验记录和记录证据化结论的工具。
- Agent 可以通过 Control 的受限远端工作区工具读取/修改项目、查看 Git diff 和上一轮结果，创建 DRAFT Plan。
- Plan preview 返回结构化差异和展开后的 Job。
- Agent 只能 `request_plan_approval`；用户在本地 UI/CLI 确认 revision + spec hash 后才调用内部 `approve_plan` 产生 Job。
- MCP 只获得 agent scope；批准使用 owner scope，交互式 CLI 不接受静默非 TTY 批准。
- 工具响应保持短小，原始日志按需获取。
- 不在 AutoLab 中保存 GLM API Key 或代理模型请求。
- 首先使用 GLM Coding Plan + Claude Code Agent 外壳验收，再选一个支持 MCP 的 GLM 宿主做兼容验证。

真实演示：

```text
用户：在两个数据集上各跑 3 个 seed
→ Agent 创建计划并解释
→ Agent 请求审批，用户在本地 UI/CLI 确认
→ 6 个任务排队执行
→ Agent 总结结果
→ 结论引用具体 Job/Artifact，并在失败时记录重新考虑条件
→ 用户要求改学习率
→ revision 2 被创建并执行
```

通过门：GLM Agent 连续完成 3 轮，无需在控制台手工拼装任务；更换 Agent 宿主后无需修改 Control、Runner、数据库或 MCP 工具 schema。

## M5：保留 Multica 体验的薄控制台

目标：保留用户喜欢的高密度 Shell、横向看板、卡片和 GPU 页面体验，为长任务提供稳定观察和少量人工操作，同时不恢复协作产品内核。

开工前必须完成许可决策：已授权迁移、内部保留 Multica 品牌、或不读取源码的独立实现。未完成决策不得解压快照或使用 `source-assets/brand/`。

实现顺序：

1. 按许可决策移植或独立实现 design tokens、Sidebar、PageHeader 和 Dashboard shell。
2. 用轻量 `BoardCardView[]` 重建横向科研看板；列由 Plan/Job 实况派生。
3. Run Detail + 增量日志。
4. Plan Workspace preview/approve。
5. GPU Servers 页面。

性能通过门：

- Overview 只有 1 个业务请求。
- 事件只更新对应 Job 和相关摘要。
- 连接正常时无 5 秒轮询。
- 1000 个历史 Job 下首屏仍小于 1 秒。
- 生产 bundle 不包含富文本、Mermaid、Gantt、营销站或通用协作模块。

## M6：真实使用期

目标：用产品实际完成 10 轮研究迭代，再决定下一步。

每轮记录：

- 用户原始要求。
- Agent 生成的 Plan 差异。
- 排队和执行中遇到的人工介入。
- 结果是否足以支持下一轮决策。
- 哪些操作仍需手工 SSH。
- 新会话是否能仅依靠 `.autolab/` 和产品 API 恢复研究上下文。

10 轮后只从重复出现的问题中选择 P1，不从旧需求文档恢复功能。

## 开发决策规则

新增需求进入当前里程碑前，必须回答：

1. 它阻塞了哪个正在验收的用户流程？
2. 能否作为 JSON 字段或派生视图解决，而不是新表或新状态？
3. 去掉它是否仍能完成本轮真实训练？
4. 它会不会让一次任务事件影响无关页面？
5. 是否有可在真实进程上验证的完成标准？
6. 它属于研究语义还是运行事实，权威来源是否唯一？

如果第 1 或第 5 个问题没有明确答案，进入 backlog。

## 明确的止损线

出现以下任一情况应暂停功能开发并做架构评审：

- P0 表超过 10 张。
- Job 以外再次出现跨十余状态的主业务状态机。
- 同一状态开始同时写入 Markdown、数据库和前端缓存。
- 核心页面初始请求超过 5 个。
- 需要通过兼容层模拟另一套产品 API。
- AutoLab 自有业务前端在 P0 超过 20,000 行，或为了复用一个视觉组件重新引入大块 Multica 领域内核。
- 连续两周没有在真实服务器上完成新的用户闭环。
- 测试全部通过，但用户仍需频繁手工 SSH 修复系统状态。
