# 交给编码 AI 的开工方案

版本：v1.3  
目标：从空仓库实现 AutoLab Lite 的第一个可运行纵切，不在旧 AutoLab 上继续叠加。

## 1. 本轮任务

本轮只完成 M0 和 M1：

```text
初始化一个已有代码项目
→ 建立最小科研资产目录
→ 创建实验记录和 DRAFT Plan
→ 用户批准 Plan
→ 展开 3 个本地 Job
→ Control 按并发 1 调度 Runner
→ 增量读取日志
→ 收集 metrics.json 和产物
→ 全部 Job 进入终态且 GPU Lease 全部释放
```

暂不实现 Web、SSH、真实 GPU、MCP、模型 API、RD-Agent、报告或多 Agent 编排。M0/M1 先把未来 GLM MCP 会调用的底层能力通过 CLI 验证完整。

## 3. 不可更改的架构决定

### 3.1 权威来源

- `.autolab/`：研究目标、假设、成功判据、结论和失败经验。
- Control SQLite：Plan 批准、Job、Lease、事件和 Artifact 索引。
- Runner：控制端离线期间的远端进程事实。
- UI/ViewModel：纯派生，不保存业务状态。

### 3.2 权限边界

- Agent 可以创建 DRAFT Plan 和请求审批，不能直接生成 Job。
- M0/M1 的 `plan approve` 是用户主动执行的 CLI 操作。未来普通 MCP 不暴露 `approve_plan`。
- Runner 只执行不可变 Manifest，不解释自然语言。
- GPU Lease、等待顺序和并发只由 Control 管理；Runner 不维护第二套队列。
- 网络 I/O 不得发生在 SQLite 写事务中。

### 3.3 规模边界

- P0 从 7 张业务表开始：servers、projects、plan_revisions、jobs、gpu_leases、job_events、artifacts。
- 不新增 project/run/attempt 三层状态机。
- 不新增通用 outbox、事件总线、插件平台或 Provider 框架，除非当前本地 E2E 已证明缺少它就无法正确恢复。
- 不引入 Redis、Celery、PostgreSQL、Docker 编排或前端工程。

## 4. 推荐技术基线

- Control 与开发工具使用 Python 3.12
- Runner 支持 Python 3.10+；CI 至少覆盖 3.10 和当前开发版本
- `uv` 管理环境与 lockfile
- FastAPI + Uvicorn
- SQLite WAL；可使用标准库 `sqlite3`
- Pydantic v2 / JSON Schema 定义协议
- Typer 或简单 argparse CLI，二选一
- pytest + asyncio 测试
- Ruff；类型检查可选，但不能阻塞第一个纵切

目录建议：

```text
├── apps/
│   └── control/
│       ├── autolab_control/
│       └── tests/
├── runner/
│   ├── autolab_runner/

├── packages/

```

如果编码 AI 有充分理由调整目录，可以调整；产品边界和协议所有权不能调整。

## 5. 实施顺序

每一步都必须保持主分支可运行。不要先写完整架构再做集成。

### Step 0：仓库护栏

交付：

- Python workspace、依赖锁、基础 lint/test 命令。
- README 只写真实可运行命令。
- `docs/decisions.md`，记录新增表、状态或依赖的理由。
- 禁止提交 `.env`、密钥、数据库、日志、输出和虚拟环境。

验收：空仓库中执行测试命令成功，Control 和 Runner 均有可导入包。

### Step 1：协议先行

把 `source-assets/contracts-v1/` 复制到正式 protocol package，生成相应语言模型并测试：

- `PlanSpecV1`
- `ManifestV1`
- `RunnerEventV1`
- `ArtifactV1`
- 矩阵展开函数
- canonical JSON/hash 函数

不得兼容旧 `m1/1` envelope、`/attempts` 路径或旧状态名。Job 状态和 Runner 观察状态按 contracts README 分开实现。

`PlanSpecV1` 至少包含：

```text
project_id
experiment_ref / experiment_hash
hypothesis / change_from_previous
baseline / metrics / success_criteria
code_anchor
command_template
matrix 或 explicit_jobs
resources / timeout_seconds
outputs
```

验收：

- 2 datasets × 3 seeds 稳定展开为 6 个顺序固定的 Job。
- 相同输入产生相同 hash。
- 缺 success criteria、命令或输出规则时校验失败。

### Step 2：最小科研资产协议

以 `source-assets/research-protocol/` 为规范模板，实现窄函数或 CLI：

- `research init <project-dir>`
- `research create-experiment`
- `research validate`
- `research record-conclusion`

只生成：

```text
.autolab/context.md
.autolab/experiments/EXP-xxxx.md
.autolab/knowledge/failures.md
```

规则：

- 实验记录必须包含 hypothesis、baseline、metrics、success criteria、risk/fallback。
- 不得写入 QUEUED、RUNNING 或 GPU 状态。
- `record-conclusion` 必须引用至少一个 Job、Artifact 或指标文件。
- rejected/stop 结论必须包含重新考虑条件。

验收：人工修改 Markdown 后仍能校验；新会话无需聊天记录即可理解实验目的和上轮结论。

### Step 3：从零实现最小 Runner

以 `contracts-v1/` 和 `gpu-agent/REFERENCE_ONLY.md` 为规范，从测试出发实现；旧源码只能参考局部算法：

- `POST /jobs`：按 `dispatch_id` 幂等接收。
- `GET /jobs/{id}`：返回快照和最新事件序号。
- `GET /jobs/{id}/logs?cursor=`：增量日志。
- 每个 Job 独立进程组、日志和输出目录；状态与事件持久化到 Runner 本地存储。
- Control 断开后任务继续运行。
- 非 test mode 下 Token/HMAC 为空时拒绝启动。
- 使用 argv + `shell=False`，cwd 为登记项目 workdir。
- 对 workdir/output 做允许根、`realpath` 和 symlink containment。
- 状态变更与事件追加原子提交；持久化安全进程身份，不能只凭 PID 恢复或杀进程。
- Runner 不排队；GPU 已被占用时明确拒绝。

M1 的 local transport 可使用伪 GPU 槽位，例如 `local:0`，但 Lease 语义必须与未来真实 GPU 一致。

验收：同一 `dispatch_id` 连续和并发提交都只启动一个 OS 进程；异载荷冲突、空凭据、路径越界、陈旧 PID 和无内部排队测试通过。

### Step 4：Control 数据和事务

只建立需求中的 7 张业务表。首先实现以下事务：

1. `create_draft_plan`
2. `approve_plan_from_local_user`
3. `acquire_lease`
4. `confirm_dispatch`
5. `ingest_event`
6. `release_lease`

关键约束：

- Plan 批准时读取并保存 `experiment_hash`。
- CLI 批准必须使用 owner scope、要求交互式 TTY 并校验用户看到的 `spec_hash`；API 内部记录 `approved_by=local_cli`。自动 E2E 只能使用显式 test mode 的测试 owner capability。
- APPROVED Plan 不可修改。
- `(plan_revision_id, ordinal)` 唯一。
- `dispatch_id` 全局唯一。
- 活跃 Lease 对 `(server_id, gpu_index)` 唯一。
- 多 GPU Job 在同一事务中全有或全无地获取 Lease，不能部分持有后等待。
- `(runner_instance_id, event_seq)` 唯一。
- 重放批准、派发和事件不会重复产生副作用。

验收：所有事务有并发或重放测试；事务内不调用 Runner。

### Step 5：Scheduler 和 local transport

实现最小循环：

```text
选最早 QUEUED Job
→ 原子获取 Lease 并标记 DISPATCHING
→ 事务外调用 Runner
→ 保存 remote_job_id / RUNNING
→ 增量消费事件
→ 终态释放 Lease并登记 Artifact
```

派发失败时不得丢 Job 或永久占住 Lease。首先使用明确、有限的恢复策略，不做无限自动重试。

`dispatch_id` 必须在网络调用前持久化。若 POST 在 Runner 已受理后超时，Job 保持 DISPATCHING，Control 使用同一 dispatch_id 重放或查询 Runner；在确认远端未受理或进入真实终态前不得生成新 dispatch_id，也不得把未知结果直接标 FAILED。

### Step 6：CLI 和本地 E2E

CLI 至少支持：

```text
server add-local
project add
research init
experiment create
plan create
plan preview
plan approve --expect-spec-hash <hash>
job list
job show
job logs
```

端到端测试必须启动真实 Control 与 Runner 双进程，不能 mock Runner：

1. 创建临时项目和 `.autolab/`。
2. 创建一个有明确成功判据的实验记录。
3. 创建并批准含 3 个 Job 的 Plan，并发限制为 1。
4. 每个 Job 输出多行日志、`metrics.json` 和一个小 Artifact。
5. 验证 Job 串行运行、日志按 cursor 增量读取、产物 hash 正确。
6. 重放批准与派发请求。
7. 注入一次“Runner 已受理但 Control 响应超时”，验证重试仍只启动一个进程。
8. 验证只执行 3 个进程，全部终态，Lease 为 0。

该 E2E 连续运行 20 次全部通过，M1 才完成。

## 6. 建议提交顺序

1. `chore: scaffold autolab-lite workspace`
2. `feat(protocol): add plan manifest and event v1`
3. `feat(research): add minimal file-based research records`
4. `feat(runner): execute manifest idempotently`
5. `feat(control): add minimal schema and plan approval`
6. `feat(control): schedule local jobs with persistent leases`
7. `feat(cli): expose local experiment workflow`
8. `test(e2e): verify local three-job execution`

不要为了形成这些提交而牺牲可运行性；如果工作环境要求单次交付，也应按此顺序实现和验证。

## 7. 本轮完成定义

只有同时满足以下条件，才可以报告 M0/M1 完成：

- `research validate` 通过。
- 协议单测、事务单测和真实双进程 E2E 全绿。
- E2E 连续 20 次无重复派发、无 Lease 泄漏。
- Control 重启前后数据库可正常打开；M2 的完整恢复测试可暂不实现。
- Runner 的 fail-closed、路径边界、并发幂等和进程身份测试全绿。
- 生产代码中没有 RD-Agent、LLM Provider、旧 AutoLab migration 或 Multica core 依赖。
- 没有 Web 页面或占位前端工程。
- 文档中的启动命令由编码 AI 实际执行过。

## 8. 编码 AI 的汇报格式

每完成一个 Step，只汇报：

1. 已实现的用户可观察行为。
2. 新增的表、状态和依赖，以及必要理由。
3. 实际执行的验证命令和结果。
4. 尚未完成或存在不确定性的部分。

禁止用“架构已搭好”“基本完成”代替可执行证据。

## 9. 后续阶段，不属于本轮

- M2：取消、`POST /jobs/{id}/stop`、重试、Control/Runner 重启和断线对账；不可达使用 observation UNKNOWN，不写 LOST 终态。
- M3：SSH 指纹固定、凭据、Runner 安全部署、真实 GPU、远端 Artifact，以及受限项目文件/Git 原语。
- M4：本地 MCP server；Agent 只能请求审批，用户在 UI/CLI 批准；使用 GLM Coding Plan + Claude Code Agent 外壳完成连续三轮实验，并验证第二个 GLM 宿主。
- M5：先通过许可决策门，再选择已授权移植、内部保留品牌或独立实现 Shell/看板/计划页/运行页/GPU Servers。
- M6：真实研究项目连续十轮使用，再决定自动分析、报告或自主 Planner。
