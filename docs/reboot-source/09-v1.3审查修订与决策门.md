# v1.3 审查修订与决策门

## 1. 本版结论

v1.3 把本交接包从“需求与旧代码合集”收紧为“可实施的 M0/M1 基线”。编码 AI 可以在新仓库实现 M0/M1，但无权自行提前进入 SSH、MCP、Web 或 Multica 迁移。

规范优先级从高到低为：

1. `source-assets/contracts-v1/` 中的新协议；
2. `01-产品需求-v1.0.md` 与 `02-目标架构与数据模型.md`；
3. `08-交给编码AI的开工方案.md`；
4. reference 代码和旧测试。

低优先级资产与高优先级规范冲突时，必须重写低优先级实现，不能为了让旧代码继续运行而修改新协议。

## 2. v1.3 已修正的问题

- 旧 gpu-agent 不再标为可直接迁入；它保留为进程组、幂等、事件和停止链的实现参考。
- 新增 `PlanSpecV1`、`ManifestV1`、`RunnerEventV1`、`ArtifactV1` JSON Schema。
- 新增 `.autolab/context.md`、实验记录和失败经验模板。
- Job 执行状态与 Runner 连接观察状态分离；`LOST/未知` 是 UI 观察结果，不是不可恢复的 Job 终态。
- Agent 不能直接调用人类批准操作；MCP 只允许请求审批和查询审批结果。
- 明确远端项目的读写路径：Agent → 本地 MCP → Control → SSH/SFTP → 登记项目根目录。
- 明确 Runner fail-closed、路径 containment、单一调度权、进程身份和原子事件要求。
- 对 Multica 源码、截图和品牌资产增加许可决策门。
- Control 使用 Python 3.12；Runner 目标兼容 Python 3.10+，并要求在 CI 覆盖最低版本。
- M1 不再把用户停止链作为完成范围；取消、停止和恢复统一进入 M2。

- 使用 local transport、伪 GPU 槽位和真实双进程 E2E；
- 为当前用户流程增加必要测试。

禁止：

- 修改规范以迁就旧 `/attempts`、project/run/attempt 状态机或 fixture API；
- 实现 Web、SSH、真实 GPU、MCP、模型调用、RD-Agent 或多 Agent 编排；

## 4. M1 开工门

进入 Runner/Control 编码前必须先通过：

- 四个新 JSON Schema 可被解析，样例正反例测试齐全；
- `.autolab` 模板可初始化、人工编辑并重新校验；
- Job 状态、观察状态和事件到投影的映射有测试；
- 同一 Plan 展开顺序和 hash 稳定；
- `dispatch_id` 在网络调用前持久化，超时重试复用同一个值；
- 明确只有 Control 分配 GPU Lease，Runner 不维护第二套等待队列。

## 5. M2 决策门：取消、停止与恢复

M2 开工前冻结：

- QUEUED 取消与 RUNNING 停止的状态边；
- TERM grace KILL 的时间和事件语义；
- Control 在 POST 成功但响应丢失时的对账；
- Runner 快照、事件游标过期和进程身份校验；
- Runner 不可达时 `observation_state=UNKNOWN` 的 UI 表达；
- 终态不回退，但非终态可在对账后恢复 RUNNING 或进入真实终态。

## 6. M3 决策门：SSH 与真实服务器

M3 开工前必须完成安全设计：

- 首次连接使用 TOFU 并展示主机指纹，后续连接固定指纹；禁止 `known_hosts=None`。
- SSH 命令参数使用可靠转义或 SFTP，不把 Token 拼进远端 shell。
- Runner 使用 0600 配置或服务管理器注入凭据，不允许空 Token 启动。
- 登记每个服务器允许的项目根和输出根；所有路径使用 `realpath` 后做 containment 校验。
- 部署/升级精确定位服务实例，禁止宽泛 `pkill -f`。
- Runner 最低 Python 版本在真实服务器验证，并由 lockfile/构建产物覆盖。

## 7. M4 决策门：GLM Agent 与人类批准

默认拓扑：GLM Agent 运行在用户工作站，通过本地 stdio MCP 调用 Control；Control 使用 SSH/SFTP 访问远端项目。

MCP 分两类：

- Agent 工具：读取项目、读取/修改受限文件、查看 Git diff、创建 DRAFT、请求审批、查询 Job 和记录结论。
- 人类操作：批准 Plan、删除凭据、强制停止、覆盖产物。只由 owner-scope 本地 UI/交互式 TTY CLI 提供，不暴露为普通 MCP 工具。

Control 区分 agent/owner capability。MCP 子进程只获得 agent scope；owner 凭据保存在系统钥匙串或本地 App 进程内，不进入 MCP 配置、环境或日志。CLI 批准要求交互式 TTY 并输入 plan 短 hash，或调用系统级用户确认；非交互脚本只能在显式 test mode 使用测试 owner capability。

若未来某个 Agent 宿主提供可信的人机确认回调，可以增加适配器，把一次性审批凭据绑定到 `plan_revision_id + spec_hash + expires_at`；不得仅靠提示词声称“用户已经同意”。

远端工作区写工具必须：

- 只允许登记项目根目录内的相对路径；
- 拒绝 `..`、绝对路径和越界 symlink；
- 以 patch 预览和 hash/CAS 防止覆盖并发修改；
- 返回 Git status/diff，不自动提交或推送；
- 不提供通用、无限制的远端 shell MCP 工具。

## 8. M5 决策门：Multica 许可与 UI 路径

Multica 快照内的许可证包含额外的托管、商业嵌入和品牌条件。M5 只能从以下路径中选择一条并记录决定：

1. **已授权迁移**：已取得适用的 commercial license 和必要的 branding waiver，再按许可证移植源码。
2. **内部保留品牌**：仅在单一组织内部使用，保留许可证要求的 Multica 品牌和归属。
3. **独立实现**：不读取或复制 Multica UI 源码、图标和具体组件结构，只根据 AutoLab 功能需求、通用设计原则和自主设计稿实现。

未记录选择前：

- `source-assets/ui-reference/multica-shell-source-reference.tar.gz` 不得解压到新产品仓库；
- `source-assets/brand/` 不得作为 AutoLab 品牌资产；
- 可以实现与来源无关的通用能力，例如深色主题、左侧导航、横向任务板和服务器遥测卡片，但不能要求像素级复刻。
