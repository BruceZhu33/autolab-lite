## ADD-1 预算降额不可达终态（reduction 记录模型）

**动机**：降额两阶段（V6）在排空中真实消耗可能越过 target（B=100、C=20、R=40、target=50，再耗 35 → C=55>50）。r3 契约已将账本不等式改为 `R ≤ max(0, B−C)`（真实用量永远可入账，C 超限自动禁新预留）；剩余缺口是**降额请求的终局语义**。

**条款（单一方案）**：

1. `budget_accounts.status` 维持 `ACTIVE|DRAINING` 不变（r2 旧文的 TARGET_UNATTAINABLE 状态**废弃**）。
2. 新表 `budget_reductions(id, project_id, requested_limit_s, status, created_at, finalized_at)`，
   `status ∈ PENDING|SETTLED|UNATTAINABLE|SUPERSEDED`——降额是**有历史的独立记录**。
3. 受理（202 accepted）写 PENDING；对账器在每次结算后评估：
   - `C+R ≤ requested` → 原子切换账本（limit=requested、回 ACTIVE）+ reduction 置 SETTLED；
   - `R=0 ∧ C>requested`（终值必超）→ 置 **UNATTAINABLE**（维持原 limit；停止继续发 STOP）。
4. 新降额请求受理时，旧 PENDING/UNATTAINABLE 记录置 **SUPERSEDED**（被替换，不再生效）。
5. 幂等语义：`POST /budget/reduction` 同键重放**始终返回原响应**（202 accepted 或 200 achieved，
   api_idempotency 不变）；当前终局经 `GET /budget`（返回 reduction 状态列表）与 WS
   `budget.reduction_settled|unattainable` 查询——重放与查询职责分离。
6. `metering_policy.stop_grace_s / error_tolerance_s`（plan，D32）在 T-AUTHORIZE-DISPATCH 中按
   **双层额度**处理（r4-A3）：`execution_cap = max(0, min(requested, allocatable − grace − tolerance))`
   为远端可执行额度（manifest 携带 execution_cap 与绝对截止时间）；
   **账本 R 记 `reserved_total = execution_cap + grace + tolerance`**——余量真实占用预算，
   其他任务不可侵蚀；观测超额经 overage_s 记账（draft.6 契约已落）。
   **r5-A3 修正**：
   a. **最低可派发 guard**：`allocatable < grace + tolerance` 时直接拒绝（EXECUTION_CAP_NOT_POSITIVE），
      不得产生 cap=0 而 reserved_total>allocatable 的"死额度"授权；
   b. **消耗上界证明义务**：远端实际消耗的可证明上界 = `execution_cap + stop_grace`（agent 硬截止
      强制停机 + 宽限期内的计量采样）；该上界 ≤ reserved_total ≤ 分配时余量，因此
      `C 的渐近上界 = B`——远端违约超出该上界的观测（计量误差超容差/agent 故障）记入 overage_s
      并触发 **BUDGET_BROKEN**（draft.6 已实现：overage>0 时一切新授权被拒，直到人工对账处置）——
      系统不变量破坏被显式暴露而非放宽 C+R≤B。
   c. 例外路径：overage 处置后（人工确认债务、调整 limit_s 或放弃余额）经审计事务清零 overage_s
      恢复授权，全程留痕。

**受影响契约**：schema（新表）、transactions §4、openapi（GET /budget 响应）、ws-events（新事件）。

## ADD-2 test 后继续开发：子项目版本（唯一方案）

**动机**（r3 裁决：子项目方案，旧 experiments 方案废弃）：v2.7 §1 要求"读取 test 后继续开发=只能开新实验版本并标记原测试集已参与开发"，需在不波及全部 project FK 的前提下落地血缘。

**条款**：

1. `projects` 增列：`parent_project_id`（自引用 FK）、`origin_test_release_id`（FK→test_result_releases，
   closure trigger：该 release 须经 batch→candidate→run 链属于父项目）。
2. **创建事务** `T-SPAWN-CHILD-PROJECT`（幂等，Idempotency-Key）：单事务完成——
   校验父项目已 REPORTED ∧ release 存在且属父项目（父链闭包）→ 创建子项目（**INIT——
   与主状态机一致，经正常主链进入 REVIEW_GATE，无特权起点**）→ 追加 **append-only 记录表
   `test_set_participations(id, release_id FK UNIQUE, project_id, participated_at)`**（r4-A4：
   不修改不可变的 release 行）→ 写 audit。**唯一性**：同一 release 至多一个子项目
   （UNIQUE(origin_test_release_id)）；同键重放幂等返回既有子项目（载荷 hash 比较）。
3. **继承语义**：文献（papers）与模块档案（modules）**复制引用**（行复制到子项目，不共享行——
   原项目封存只读）；plan_protocols、runs、batches、评测结果**不继承**——子项目经主链
   （INIT→…→REVIEW_GATE）重建协议链（D44 全量失效传播由"新项目=新比较集作用域"天然保证）。
4. 子项目走现有项目状态机（INIT→…），**不视为**父项目状态回退；父项目保持 REPORTED 永久封存。
5. API：`POST /api/v1/projects/{id}/spawn-child`（guard：父已释放；返回子项目 id）；
   `GET /api/v1/projects/{id}/lineage`（父/子/release 链）。

**受影响契约**：schema（两列+trigger+标记）、openapi（两端点）、state-machine（新增迁移注记：
REPORTED +spawn_child → 子项目 INIT，属"派生"非父态迁移）、T-SPAWN 事务模板。

## ADD-3 报告产物归属（双 FK + 关联表）

**动机**（r3 裁决确认方向，补同项目闭包）：Q05 要求任何终态可产出阶段报告，artifacts 当前强制 attempt_id。

**条款**：

1. `artifacts` 增 `project_id`（nullable FK）；约束为**恰好归属其一**（r4-A5 修正写反的表达式）：
   `CHECK ((attempt_id IS NOT NULL) <> (project_id IS NOT NULL))`——两非空或两空均拒绝；
   attempt 产物保持 attempt_id 非空、project_id NULL。
2. 新表 `reports(id, project_id FK, kind ∈ stage|final, stats_json, generated_by ∈ llm|deterministic, created_at)`
   与关联表 `report_artifacts(report_id FK, artifact_id FK, PRIMARY KEY(report_id, artifact_id))`。
3. **同项目闭包 trigger**：report→artifact（经关联表）与 artifact.project/attempt 归属必须同项目。
4. final 报告 guard：项目 `origin_test_release_id`（ADD-2）或直接关联的 release 存在且属同项目。
5. reports 与 report_artifacts **append-only**（重生成=新 report 版本行，不 UPDATE）。

**受影响契约**：schema、openapi（reports 响应模型落库）、transactions（T-REPORT）。

## ADD-4 评审对话实体（规范化、收窄接口）

**动机**（r3 裁决确认方向，补唯一性与 guard 细则）：P4 对话式评审需要持久化 thread/turn/反问/确认。

**条款**：

1. `review_threads(id, project_id, module_id NULL, kind ∈ per_module|integral, status ∈ open|concluded,
   conclude_revision)`——conclude 走 CAS。**结构闭包（r4-A6）**：
   `CHECK ((kind='per_module' AND module_id IS NOT NULL) OR (kind='integral' AND module_id IS NULL))`；
   module 与 thread 同项目（closure trigger）；**部分唯一索引**：每项目每模块至多一个有效 thread
   （UNIQUE(project_id, module_id) WHERE kind='per_module'）∧ 每项目恰一个 integral thread
   （UNIQUE(project_id) WHERE kind='integral'）。
2. `review_turns(id, thread_id, seq, role ∈ user|assistant|system, content, idempotency_key, created_at)`——
   append-only（no UPDATE/DELETE trigger）；`UNIQUE(thread_id, seq)`、`UNIQUE(thread_id, idempotency_key)`。
3. `review_questions(id, thread_id, body, created_at)`（规范化）与
   `review_confirmations(id, question_id FK UNIQUE, answered_at, answer)`——一问题至多一次确认。
4. **接口收窄为 create/list/answer/conclude 四操作**（无 update/delete）；answer 写 confirmations，
   conclude 校验本 thread 全部 question 已确认。
5. **D21 guard 强化（T-FREEZE F5）**：本项目**存在**（非真空）per_module threads 覆盖全部已登记
   modules ∧ 各自 concluded ∧ **恰一个** integral thread concluded ∧ 全部 questions confirmed——
   零 thread 项目不得通过 F5（防真空放行）。

**受影响契约**：schema、openapi（P4 四端点替代 BLOCKED 占位）、plan.schema.json（review_conclusions
引用 thread 汇总）、T-FREEZE。

## ADD-5 远端硬截止组合语义（**已冻结 · 已落契约 draft.4**）

冻结内容（不再变动）：本地时钟超过 expires_at 且无 agent 回执 → `ATTEMPT_STOP_UNKNOWN`（不虚报）；
agent `deadline_exceeded` **可信回执**（携带最终累计 usage、退出原因、attempt/dispatch/epoch）→
`deadline_exceeded_ack` → `STOP_CONFIRMED` 并在**同一 T-INGEST** 完成最终 usage 入账与结算
（`settle_reason=hard_deadline`）。已落：state-machine.yaml v3 边、transactions.md §6、
schema 状态枚举、tests/test_agent_ingest.py::test_deadline_exceeded_ack_settles_atomically；r5 补停止链 snapshot_reconciled 边。
