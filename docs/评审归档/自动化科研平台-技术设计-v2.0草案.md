## 1. 系统架构与可信边界（S1）

```
┌─────────────────── 用户控制机（mac/Win/Linux）───────────────────┐
│  Tauri 壳 ─▶ Next.js 前端(static export) ─HTTP/WS─▶ sidecar       │
│            (Python3.12 · FastAPI · SQLite WAL · RD-Agent 引擎)    │
│            sidecar 仅绑定 127.0.0.1 随机端口 + 启动期 capability   │
│            token（壳注入，防本机其他进程/网页调用）（B2）           │
└────────────────────────── SSH 隧道 ─────────────────────────────┘
                │
   ┌────────────▼─────────────────────────────────────┐
   │ GPU 服务器（Linux）· gpu-agent                     │
   │  ┌─────────────────┐  ┌────────────────────────┐  │
   │  │ 执行身份 A：train │  │ 执行身份 B：eval（独立    │  │
   │  │ Unix 用户 autolab-│  │ Unix 用户 autolab-eval， │  │
   │  │ train             │  │ 评测资产对其不可见）       │  │
   │  └─────────────────┘  └────────────────────────┘  │
   │  一卡一队列 · 双 profile · 远端硬截止                │
   └───────────────────────────────────────────────────┘
```

**执行身份分离（S1 核心设计）**：
- 服务器上建两个 Unix 用户：`autolab-train`（训练身份）/ `autolab-eval`（评测身份）。
- 评测资产（冻结的评测代码、测试集、聚合规则）归 `autolab-eval` 所有、权限 750/640，**训练身份不可读**——这是 OS 级边界，不依赖代码自觉。
- gpu-agent 任务带 `profile: train|eval` 字段，以对应用户执行；环境部署脚本一次性完成双用户初始化。
- `trusted_metrics` **只能由评测 profile 任务通过 agent 的受控回传通道写入**（sidecar 校验任务 profile + 五元组 digest：evaluator digest、protocol digest、数据版本、split、checkpoint hash、证据产物 hash），不接受任何 train profile 来源。
- 妥协声明：单机内仍同硬件，不防御内核级威胁（自用威胁模型，见选型"已知权衡"）。

## 2. 控制权边界与调用时序（S2）

**RD-Agent 降格为"提案引擎"**：`evolve_iter` 一次调用只允许产出【分析结论 + patch 提案（diff）】，不产生任何副作用。所有副作用由产品层显式提交：

```
循环控制器（产品层，每轮）：
 1 JUDGE 三查（取消/预算/plan epoch）           ← 数据库 CAS
 2 调 RD-Agent：输入上下文 → 返回 {analysis, patch_diff}   ← 纯函数式
 3 产品层：应用 patch → lint/冒烟 → git commit（code_snapshot 登记 hash）
 4 产品层：预算预留（账本事务）→ 组装执行清单（digest）→ 派发 attempt
 5 gpu-agent 按清单执行（train profile）→ 事件回传（幂等）
 6 产品层：调度评测（eval profile）→ trusted_metrics 入库
 7 产品层：结果齐套判定 → 状态迁移（expected_state CAS）→ 下一轮 JUDGE
```

- **RD-Agent 版本固定**（requirements 锁版本号），适配器契约 = §2 时序中它的输入输出两接口；升级 = 显式重新评估。
- 崩溃恢复：状态机 + outbox（§5）保证不重放 patch、不重复派发——重放需通过 attempt 幂等键。

## 3. 数据模型（S3/S4/S5 —— 分五组，约 25 表）

**核心实体**：`servers` `gpus` `projects` `project_gpus`（卡池）
**执行与产物**：
- `code_snapshots(id, project_id, commit_sha, export_hash, lfs_note, created_at)`——run 绑定快照而非裸 SHA（B5）
- `environment_versions(id, project_id, ver, spec_hash, frozen_spec)`
- `data_versions(id, project_id, name, ver, manifest_sha)` `data_replicas(server_id, data_version_id, logical_path, actual_path, status)`
- `runs(id, project_id, round_no, role, plan_proto_id, code_snapshot_id, env_ver, data_ver, candidate_id, init_protocol, parent_run_id, load_report, cum_steps, status)`
- `attempts(id, run_id, seq, dispatch_id UNIQUE, server_id, gpu_index, profile, exec_manifest_hash, budget_reservation_id, status, rc)`——run/attempt 分离（S4）
- `artifacts(id, attempt_id, kind, path, sha256, protected)`
**计划双轨（B7）**：
- `plan_protocols(id, project_id, ver, body_hash, frozen_yaml)`——不可变协议快照
- `control_state(id, project_id, epoch, budget_limit, enabled_terms_json)`——可即时生效的控制面
- `control_events(id, project_id, epoch_from, epoch_to, change_json, t)`——控制变更历史，已排队任务绑定 epoch
**科研证据**：
- `candidates(id, project_id, proto_id, selection_rule_ver, selected_run_id, status)`（D37）
- `training_recipes(id, run_id, budget_ep, pretrain_src, optimizer, augment, precision, selection_rule)`（R10）
- `batches(id, candidate_id, proto_id, recipe_id, matrix_ver)` `batch_items(batch_id, run_id, kind, status, fail_reason)`（D45 批次身份）
- `seeds_registered(proto_id, role, seed_set_json)`（D34 预登记）
- `evaluation_results(id, attempt_id, scope[val|test], metric, value, evaluator_digest, protocol_digest, data_ver, split_ver, ckpt_hash, evidence_hash)`——trusted 唯一入口（D29）
- `splits(id, proto_id, name, unit_rule, cross_check_result, preprocess_fit_scope)`（D43）
- `baseline_acceptances(id, project_id, run_id, verdict, patch_class[compat|method], notes)`（D33）
- `review_evidence(id, review_session_id, retrieval_mode, query, sources_json, checked_at)`（D42）
**预算账本（S3）**：
- `budget_accounts(project_id PK, limit_s, consumed_s, reserved_s, revision)`
- `budget_reservations(id, attempt_id UNIQUE, authorized_s, remaining_s, status[active|settled|expired], expires_at)`
- `usage_events(id, attempt_id, seq, cumulative_s, UNIQUE(attempt_id, seq))`——追加式，乱序/重复心跳幂等
- 准入：`BEGIN IMMEDIATE` 事务内 `limit - consumed - reserved ≥ need` 校验后更新 revision；远端持有一次性授权（reservation id + authorized_s）执行硬截止
**失效与追溯（D44）**：
- `invalidation_edges(id, cause_plan_proto_id, invalidated_kind, invalidated_id, reason, revalidate_status)`

## 4. 状态机（S6 —— 三层）

- **项目层**：`INIT → ENV_SETUP → REVIEW_GATE → ACTIVE → <终态>`；终态 `COMPLETED | EXHAUSTED | CANCELLED | FAILED`，皆必经 `REPORTING` 持久态（Q05）后到达 `REPORTED`。**终态不可迁移**（含不可暂停）。
- **run 层**：`PLANNED → PATCHING → SMOKE → QUEUED → TRAINING → ANALYZING → JUDGED(继续/终止)`；失败分流态：`REPAIRING(model类) | INFRA_RETRY(基础设施) | METRIC_MISSING(阻断) | LLM_BACKOFF`。
- **attempt 层**：`DISPATCHED → RUNNING → FINISHED | FAILED | STOP_REQUESTED → STOP_SENT → STOP_CONFIRMED`（失联停在 STOP_REQUESTED 可恢复，不虚报，D31）；重连对账用**事件游标**（`GET /events?since_seq`）而非仅查 running。
- 迁移原子性：`UPDATE … WHERE id=? AND state=? AND state_revision=?`（CAS）；副作用经**事务 outbox**（`outbox(id, aggregate, op, payload, dispatched)`）投递，消除"检查后派发前"TOCTOU 窗口。

## 5. gpu-agent 契约（S4/B6）

```
GET  /healthz            → {agent_ver, schema_ver, capabilities}
GET  /events?since_seq   → 全量变更事件流（对账用，单调 seq）
POST /attempts           → {dispatch_id(幂等键), profile[train|eval],
                            exec_manifest{code_snap_ref, env_ver, data_ver, plan_proto_ver,
                            recipe_ref, init_ref, budget{reservation_id, authorized_s}},
                            manifest_digest, deadline_at}
                            agent 验证 digest 一致才入队；按 profile 切换执行用户
GET  /attempts/{dispatch_id}?tail=200
POST /attempts/{dispatch_id}/stop   → STOP_REQUESTED→STOP_SENT→STOP_CONFIRMED 状态机
POST /attempts/{dispatch_id}/usage  → {seq, cumulative_s}（幂等记账）
```

## 6. sidecar API 契约要点（S7）

统一 `/api/v1` 前缀；统一 `request_id/run_id/attempt_id/event_seq` 标识（O1）。每端点定义：请求/响应 Schema（pydantic 模型）、错误码、幂等键、状态前置条件；**完整 OpenAPI yaml 为 M1 交付物**（入口条件，见 §9）。能力面新增：数据 manifest/同步/就绪/划分校验、协议修订分类与失效、基线验收、候选选择、批次冻结、retry/resume/repair、评测提交与证据查询、attempt 对账、停止确认查询。**验收场景映射表**：需求第 11 节每个场景 ← 对应 OpenAPI 操作 + 状态迁移 + 数据库不变量三元组（随 OpenAPI 一并交付）。

## 7. 导入与快照细节（B5）

- BASE 导入：`git clone` 后**先处理未提交/未跟踪文件**（策略：默认纳入快照并登记清单，用户可选丢弃）、子模块（递归冻结 commit）、LFS（拉取后登记 pointer+oid）、符号链接（解析为实体或拒绝，登记选择）；导出 `git archive` 后计算 `export_hash` 入 `code_snapshots`。

## 8. 打包、安全与三平台（B2/B8）

- sidecar 仅绑 loopback 随机端口；Tauri 启动时注入 `AUTOLAB_PORT` + 一次性 capability token，所有 mutating 请求校验。
- 三平台验收矩阵（CI 之外，M4 前）：安装/首次启动/路径含中文与空格/单实例/异常退出恢复（对账）/sidecar 升级 schema 迁移/卸载保留数据。
- 平台差异（文件锁、进程终止、凭据库、签名）封装在 `platform/` 适配器层（D48 修订措辞）。

## 9. M1/M2 入口条件（O4 升格）

以下不再是"技术债"，而是**开工闸门**：① plan JSON Schema 定稿；② WS 事件契约（事件类型清单+seq 规则）；③ OpenAPI v1 + 验收场景映射表；④ 本文档 v2.0 经确认。
