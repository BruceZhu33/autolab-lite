## 评审结论与分档

**不建议按当前版本直接进入无人值守的自动闭环开发验收。** 主流程已覆盖从立项到报告，但“研究方案如何被约束地执行”“控制端失联后谁负责停机”“最终结论如何被独立验证”尚未闭合。

迭代期单 seed 可以作为低成本筛选；默认最终跑 3 个 seed 也可以作为起点。问题在于：当前只为最终方案安排多 seed，基线、消融、候选选择及不确定性的处理没有形成同一套实验协议，不能仅凭这两项设置认定符合科研标准。

- **严重**：可能导致自动化失控、主要科研结论失真，或核心产品承诺无法兑现；相应能力上线前必须补齐。
- **建议**：存在明确实现歧义或异常路径缺口，应补入需求与验收标准。
- **可选**：在基本闭环可靠后增强研究效率或证据强度，不作为通用准入门槛。

共列出 **12 项严重、11 项建议、3 项可选**。每项给出定位、触发场景和可落实的修改要求；文末单独核对 D1–D28。本文是本轮需求级评审的完整交付，不表示已经穷尽实现期才能暴露的全部问题。

## 一、严重

### S01｜LLM 同时能改模型和“判卷规则”，指标上升不能保证模型进步

**角度：自动化流程漏洞、科研严谨性。定位：D6/D7/D24；[3] 第 58–60 行；[4] 第 67–70 行；[6] 第 115 行。**

- **问题与场景**：全仓库开放意味着 LLM 可以改数据划分、验证样本过滤、标签映射、指标计算或日志打印。把难例从验证集剔除、把宏平均改成微平均，都可能得到更高指标，同时通过“一步冒烟”。D24 只保证指标可读取，无法保证其含义未被改变。[6] 写了测试集评估，但没有限制测试结果重新流入后续改码。
- **后果**：系统优化了评测口径，仍会将其归档为模型改进；重复依据测试结果修订方案会污染最终证据。
- **应补要求**：在产品控制侧固化独立评测协议：数据版本与划分、主指标算法和方向、聚合方式、checkpoint 选择规则。仓库可以继续开放修改，但正式评分由独立且受保护的执行器完成，协议变化必须形成新实验版本并重建可比对照。测试数据/标签按训练需要隔离，测试评分只用于预先冻结的最终实验；查看测试结果后再改模型，须明确标记原测试集已参与开发。

- **复核补充：冻结前先验证划分本身是否有效**。同一患者的不同切片、同一视频相邻帧或同一对象的重复记录，可能分散在 train/val/test；文件名和文件哈希不同并不能排除这种泄漏。应按研究问题登记真正的独立单位，按对象/组或时间约束划分并校验交叉关系。常规归纳学习下，归一化统计、特征选择等需要拟合的预处理只能从训练部分学习；若采用允许接触未标注测试数据的特定协议，则须单独声明，不能与普通留出评估混用。预处理泄漏的具体示例见 [scikit-learn 官方文档](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)。

**依据边界**：自适应重复使用留出集会造成对留出集本身的过拟合，见 [Dwork 等：Generalization in Adaptive Data Analysis and Holdout Reuse](https://arxiv.org/abs/1506.02629)。这里的独立评测执行器是针对本产品的工程建议，并非该论文规定的唯一实现。

### S02｜“复制 BASE + conda 隔离”不足以兑现用户资产不被改动

**角度：自动化流程漏洞、内部一致性。定位：D6/D7/D19/D20；[1] 第 42 行；[2] 第 49–50 行；第 164–165 行。**

- **问题与场景**：conda 隔离的是依赖环境，文档没有定义训练/改码进程的文件、网络与进程权限。复制后的代码仍可能含指向原目录的绝对路径或符号链接；生成的清理命令也可能写入数据主副本、其他项目目录或读取 SSH/LLM 密钥。
- **后果**：“用户原目录永不被自动化改动”目前只是导入语义，缺少运行时保障。紧急停止属于事后控制，不能恢复已覆盖的文件。
- **应补要求**：把可写范围限制为本项目、本次运行目录；原目录、数据主副本、控制端数据库和密钥不可由训练代码写入或读取不必要内容。规定进程及网络权限、资源上限、导入链接处理；外来论文、日志与仓库文本不得成为控制面指令。沙箱实现可选，但隔离边界与验证用例不能省略。

### S03｜重连恢复没有任务所有权协议，可能重复训练或误判已经停止

**角度：产品完整性、自动化流程漏洞。定位：D14/D15；[4] 第 75 行；第 168 行。**

- **问题与场景**：训练已在服务器启动，启动回执因 SSH 断线丢失；主服务重启后只看到本地“待执行”，再次派发。同样，紧急停止期间服务器失联，UI 无法确认远端是否已终止。需求只有“持久化、自动重连”，未定义两端状态冲突如何处理。
- **后果**：同一卡重复占用、任务重复计费、重复提交下一轮；界面显示已停止，远端仍运行。
- **应补要求**：每个 run/attempt 使用唯一 ID，派发与结果接收幂等；远端持久化任务身份、进程组和状态，重连先对账再调度。明确未知、失联、停止中、已停止等状态，未经确认不能释放卡位或宣布停机成功。远端本地执行超时/预算保护，并规定控制端长期失联时的处理方式；停止只杀该项目所属进程组。

### S04｜预算耗尽或人工叫停后，状态机会继续启动耗 GPU 的评估

**角度：自动化流程漏洞、内部一致性。定位：D27；[5] 第 78–87、111 行；[6] 第 115–117 行；第 164 行。**

- **问题与场景**：正文规定“终止＝进入 [6]”，同时 GPU 预算耗尽、墙钟超限、人工叫停的默认动作都是终止。因此预算用完或用户叫停后，系统仍可能启动消融及多 seed。另有直接冲突：第 78 行允许各条件按项目启用，第 164 行却承诺 GPU 时长预算是“硬上限”。
- **后果**：预算与停止按钮无法兑现；轮数上限也不能限制一次卡死训练、反复修复或后续批跑。
- **应补要求**：区分“搜索完成，可进入确认”“资源耗尽”“用户取消”“失败停止”。只有满足阶段准入和剩余预算的任务才能进入 [6]；取消操作不得隐式启动新训练。明确预算范围，覆盖 Round 0、失败尝试、冒烟、修复、评估、消融和多 seed；为确认阶段预留预算或单独设限。远端执行硬截止，批跑按总卡时计费；并发触发条件时，人工取消和硬限制优先于科研成功条件。

- **复核补充：判定必须先于下一轮副作用**。[4] 的步骤直接从指标分析走到改码和入队，没有把 [5] 判定插入其中。应在本轮有效结果入库后先判定科研终止条件，未终止才分析并修改下一候选；在 LLM 请求、冒烟和实际派发前再次检查取消状态及预算。状态检查与任务准入需避免竞态，不能让用户已取消时仍由旧回调提交新任务。运行期间的硬预算与超时由持续监视执行，不能等训练结束才检查。

### S05｜Round 0 没有基线验收与公平比较协议，存在“打败一个跑坏的 BASE”

**角度：科研严谨性。定位：D9/D18；[3] 第 59 行；[4] 第 64、68、72 行。**

- **问题与场景**：BASE 原版只保证代码未改，不保证数据处理、训练预算、预训练权重、优化器与原方法一致。BASE 因配置错误训练不足，后续模型通过增加 epoch、换预训练权重或增强数据而超过它，也可能被解释为结构创新有效。
- **后果**：基线对比图无法回答“收益是否来自提出的模块”；论文报告数值与本地复现数值也可能被混为同一对照。
- **应补要求**：设 Round 0 验收：训练行为、数据/指标协议、基线配置与本地结果经核验后才开始搜索；与论文数值不一致时记录可解释差异，不强行要求不同条件下完全复现。冻结关键比较条件，任何训练配方变化须披露，并增加采用相同配方的 BASE 对照。选择与论文主张匹配的公平性口径，例如相同训练步数或相同计算预算，不能默认为“一任务一卡”即公平。

- **复核补充：Round 0 失败不能直接套用普通候选的改码修复**。第 64 行要求 BASE 原版不改码，D23 又允许崩溃后自修复，二者在 Round 0 出错时的适用关系未定义。环境/路径修正与模型、数据处理、训练语义的修改须分开；必要兼容补丁应保留原快照、独立补丁版本与理由，经基线验收后再使用，不能把修过的模型仍标成“未改 BASE”。没有有效基线时，应阻断依赖基线的自动判定与优越性报告。

### S06｜只给最终方案多 seed，不能可靠支持优于基线；“均值±方差”也不清楚

**角度：科研严谨性。定位：D9/D26/D28；[4] 第 64、72 行；[6] 第 117 行；[7] 第 121 行。**

- **问题与场景**：最终模型跑 3 次，BASE 只有 Round 0 的一次。BASE 恰好是低分 seed，就会放大表面提升。迭代期没有明确 seed 是否固定或预先登记，跨轮差异还可能混入随机性。图表直接画“均值±方差”时，方差与原指标单位不同，读者容易将其误认成标准差或置信区间。
- **后果**：最终均值更稳定，并不意味着方法间差异已被可靠确认；训练随机性也不等同于不同样本划分带来的不确定性。
- **应补要求**：最终比较至少覆盖 BASE、最终模型及支撑核心结论的消融；使用预先登记的 seed 集合，保存全部有效运行和失败原因。明确随机源、聚合单位、样本数及误差棒定义，报告均值、标准差或适用的置信区间，不将方差直接当常规误差范围。根据观察到的波动与希望检测的差异决定是否追加运行；证据不足时输出“尚不能确认提升”。

**标准判断**：3–5 个 seed 不是通用的“合规线”。NeurIPS 要求说明误差来源、计算方法与误差棒含义，见 [官方 Paper Checklist 第 7 项](https://neurips.cc/public/guides/PaperChecklist)。seed 数与统计功效的关系可参考 [Colas 等的研究](https://arxiv.org/abs/1806.08295)，该文聚焦深度强化学习，不应机械地把其样本量结论套用到所有任务。

### S07｜定稿消融矩阵缺少随结构演化的规则，可能消融已经不存在的模块

**角度：科研严谨性、内部一致性。定位：D6/D10/D22；[3] 第 59 行；[4] 第 68–69 行；[6] 第 116 行。**

- **问题与场景**：定稿方案是 A+B，迭代后 A 被替换为 C，B 又与损失函数耦合；[6] 仍执行最初的 A/B 开关。即使脚本不报错，也可能只关闭了无效配置项。需求也没有说明消融需要独立重训，还是在最终 checkpoint 上关闭模块后评估。
- **后果**：消融表无法证明最终方法中各部分的贡献；推理期移除模块与训练期不使用模块回答的是不同问题。
- **应补要求**：把研究假设、模块身份、对应代码和消融配置建立映射；结构修改后使受影响的矩阵项失效并重新校验。最终确认前冻结最终代码对应的矩阵，至少包含 BASE、完整方法及支撑核心主张的关键移除项，必要时加入模块单独作用与交互对照。每项明确训练/推理干预、初始化、训练预算和 seed；不能运行的组合标记原因，不能伪填结果。自动更新若改变原定研究问题，应进入方案修订流程。

### S08｜没有“胜出方案”选择规则，也没有多 seed 确认失败后的出口

**角度：产品完整性、科研严谨性。定位：D10/D27；[4] 第 69、74 行；[5] 第 92–98 行；[6] 第 117 行。**

- **问题与场景**：第 8 轮最好，第 12 轮触发停滞，最终评估哪一个 commit？“最优 checkpoint”是某轮最佳 epoch，还是跨轮最佳模型？精度更高但时延超标的模型算不算胜出？多 seed 后不再优于 BASE，是否继续搜索、改选别的 seed，还是发布失败结论？均未定义。
- **后果**：实现者可能默认选最后一轮或测试集最高分；结果不理想时反复换候选，会引入选择偏差并突破预算。
- **应补要求**：定稿时固定候选资格、验证集选择指标、约束、平局处理及 checkpoint 规则。分别保存当前搜索版本、验证最佳候选、最终确认结果；进入 [6] 前锁定候选，不依据测试分数换人。允许“只有 BASE 可用”“未改善”“确认失败”“证据不足”等合法终态，并生成如实报告；如需新一轮研究，形成新版本而非暗中重开当前确认过程。

### S09｜experiment_plan“即时生效”会让同一实验按两套标准运行

**角度：自动化流程漏洞、科研严谨性、内部一致性。定位：D8/D21；[3] 第 59–60 行；第 162 行。**

- **问题与场景**：训练中把目标从 Dice 改为 IoU，或修改划分、seed 数和消融矩阵；已经排队的批任务使用旧配置，新完成的结果却按新计划判定。“不改写已完成记录”无法解决正在运行和排队任务归属的问题。
- **后果**：同一轮的执行与评价依据不同，跨轮比较失效；定稿人工闸门的授权范围也不明确。
- **应补要求**：每次修订生成不可变 plan_version，每个 run 绑定准确版本。区分即时控制变更与研究协议变更：降低预算、发起停止可以立即约束后续执行；指标、数据、模型假设或实验矩阵变化在明确边界生效，并决定旧队列取消、继续或迁移。涉及可比性变化的结果不得直接合并；扩大自治范围或资源上限需有明确的人工修订记录。

### S10｜“同路径、数据在位”不能证明多台服务器用的是同一份数据

**角度：自动化流程漏洞、科研严谨性。定位：D16；[1] 第 41 行；[2] 第 48–51 行；第 162 行。**

- **问题与场景**：主副本补了标签，A 已同步而 B 未同步；或者训练读取过程中 rsync 正在替换文件。两台机器路径相同、文件存在，仍然可能读到不同内容。绝对路径在其他机器上也可能无权限创建或已有别的项目数据。
- **后果**：硬件分配决定实验数据版本，结果无法比较；“自动复制到同路径”还可能覆盖用户既有文件。流程顺序只列安装、上传代码、冒烟，没有明确数据就绪必须先于数据相关冒烟。
- **应补要求**：登记数据版本、文件清单/校验信息及划分清单，训练绑定不可变版本；先同步到临时位置，校验完成后再发布，禁止更新正在被 run 使用的副本。支持逻辑数据集路径到机器实际路径的映射，目标冲突必须阻断覆盖。明确预处理与缓存也要按数据/配置版本隔离，手动放置同样需要一致性校验，不能仅检查目录存在。

### S11｜只约定项目级代码/环境副本，缺少并行消融所需的运行隔离

**角度：自动化流程漏洞、内部一致性。定位：D15/D20；[2] 第 50–51 行；[4] 第 63、68–69 行；[6] 第 116–117 行。**

- **问题与场景**：服务器 B 的两张 4090 同时跑不同消融，若共享项目目录，一个任务切换代码或改配置，另一个任务就可能读到它的内容。后续结构改动引入新依赖，自动安装到项目环境，也可能影响在跑任务。只保证“派发前版本等于本轮 commit”不保证运行期间不变。
- **后果**：记录的 commit 与实际执行内容不一致，且故障呈并发偶现，难以复现。
- **应补要求**：每个 run 使用独立、运行期间不可变的代码与配置快照、输出目录；环境按版本管理，禁止在有任务使用时原地升级。允许共享经过版本锁定的只读数据和依赖。新增依赖需重建相应环境版本并冒烟，任务绑定 commit、环境版本、数据版本及配置。该要求不必强制采用容器，但必须有等效隔离。

### S12｜链式代码迭代不等于权重续训，初始化协议缺失会把累计训练收益算成结构收益

**角度：科研严谨性、自动化流程漏洞。定位：D9/D10/D26；[4] 第 64、69、72 行；[6] 第 115–117 行。**

- **问题与场景**：文档只规定代码链式累积，没有说明各轮权重从哪里开始。BASE 从头训练 100 epoch，候选在其权重上继续训练 100 epoch，随后又继承前轮权重；名义上每轮预算相同，实际接受的训练量完全不同。结构改动还可能导致部分权重加载失败，静默跳过后实际初始化不可知。
- **后果**：跨轮上升无法归因于结构；最终“多 seed”若只是在同一训练完成的 checkpoint 上改 seed 重复推理，也没有验证训练随机性的稳健性。
- **应补要求**：每个 run 明确声明从头训练、从共同预训练权重初始化、从父候选迁移，或恢复同一次中断训练；分别记录父权重、加载/未加载参数、优化器和调度器状态、累计步数及预算。结构不兼容时必须按已批准的迁移规则处理，不能静默部分加载。探索期可用 warm start，但支持最终结构主张的比较应按统一初始化与训练协议独立重训；若主张本身包含迁移或持续训练，则比较完整流程及累计成本。最终 seed 实验须覆盖所声称的不确定性来源，不能把重复推理标为多次独立训练。

## 二、建议

### A01｜缺少训练适配契约，第一轮模块实现与指标接入没有明确落点

**角度：产品完整性、内部一致性。定位：D18/D24/D25；[1] 第 41 行；[2] 第 49 行；[3] 第 59 行；[4] 第 64–70 行。**

- **具体缺口**：D24 要求“立项时注册日志正则”，立项字段与 P3 都没有这个输入；experiment_plan 只概括“基线启动方式”，没有可执行字段契约。Round 0 之后也未明确要求先实现已定稿模块，LLM 可能直接根据 BASE 日志自由改进而跳过用户方案。
- **修改要求**：在环境搭建/评审交界处增加适配验收，明确训练与评估命令、工作目录、seed/数据/GPU 参数、指标 schema 或正则、checkpoint 位置、恢复命令和退出码。显式定义“Round 0 验收 → 实现定稿方案 → 候选冒烟 → Round 1”，并把计划与模块状态纳入每轮上下文。
- **异常验收**：日志缺失、过期文件、重复 step、NaN、百分数与小数混用、多个同名指标时，进入明确的“指标待修复”状态，不得只因正则匹配到一个数字就启动改码。

### A02｜一步冒烟不足以挡住结构级修改导致的无效训练

**角度：自动化流程漏洞、科研严谨性。定位：[2] 第 49 行；[4] 第 70 行；D23。**

- **具体场景**：模块参数未加入优化器，forward 能运行但模块没有学习；输出形状被广播后 loss 仍可计算；训练通过，但 checkpoint 无法加载或评估入口报错。
- **修改要求**：在当前“一步”的含义上补充最低验收项：前向、有限 loss、反向、预期可训练参数的梯度与更新检查、输入输出约束、保存并重载 checkpoint、最小评估链路。依赖任务语义的检查由适配配置声明；不要把所有模型都强行套用同一损失下降阈值。

### A03｜混合 GPU 卡池只检查标称显存，会卡死排队，也会污染效率对比

**角度：产品完整性、科研严谨性。定位：D15；[0] 第 34–36 行；[2] 第 51 行；[10] 第 216–221 行。**

- **具体场景**：模型改大后需求超过所有卡，任务永久等待；用户在卡上手动启动进程，平台仍认为队列空闲；BASE 在 A6000 跑、候选在 4090 跑，却直接比较时延。为适配 24GB 卡自动减 batch，还会改变实验条件。
- **修改要求**：每次结构修改后更新资源需求；无可执行卡时明确阻塞原因与处理入口。区分标称显存、当前可用资源及平台任务所有权；声明高优先级是只影响未运行任务，还是允许抢占，并处理长期饥饿。效率评测绑定同型号硬件、batch、精度模式和计时协议；跨硬件结果分组呈现。资源不足时不得静默修改科研配置。

### A04｜失败分类不足，容易把基础设施故障“修”成模型变化

**角度：自动化流程漏洞。定位：D23/D24/D27；[4] 第 71 行；[5] 第 103–105 行；第 167 行。**

- **具体场景**：服务器掉线、磁盘满、数据同步中断，可能被当成模型报错反复改码；LLM 请求超时但上游已经完成或计费，重复请求又可能生成多份改动。修复三次究竟针对一次任务、一个 round，还是一种错误，也未定义。
- **修改要求**：区分模型/代码错误、基础设施错误、指标提取错误和 LLM 服务错误。只有适合改码的错误进入模型修复；其他走限次重试、换可比执行机或暂停。规定 attempt ID、重试计数重置条件、退避和总成本上限；失败尝试虽然可不计“无提升轮数”，仍必须计预算与健康统计。LLM 输出需先完整校验再应用，断流不能留下半个补丁。

### A05｜终止条件看似齐全，但尚不能写出确定性的判定器

**角度：自动化流程漏洞、内部一致性。定位：D27；[5] 第 89–106 行。**

- **具体缺口**：“无提升”是对上一轮还是历史最好？ε 是绝对值还是相对值？“显著回退”指工程阈值还是统计显著性？train 升、val 降只适用于某些越大越好的指标，对 loss 方向相反。链式跨轮更换 loss 后，训练曲线还可能根本不可比。
- **修改要求**：每个条件给出指标方向、比较对象、统计窗口、最少有效轮数、缺失值规则、阈值单位、触发优先级及计数重置条件。把 epoch 内趋势与跨模型轮次趋势分开；不可比的 train 指标不得触发跨轮过拟合判定。摇摆检测要比较方案/结构身份，不能只比较文字摘要或 commit 是否相同。
- **文字核对**：正文实际列出 17 项条件，D27 写 14 项；动作声明只有“终止/暂停”，单轮超时却列“自修复/暂停”。后者可解释为先产生失败事件再走 D23，但必须写清这一层，而不是保留第三种未定义动作。

### A06｜“保最新 + 保最优”可能删除复现、回滚和审计依赖的产物

**角度：产品完整性、科研严谨性、内部一致性。定位：D10/D19；[4] 第 69、73–74 行；[7] 第 122 行；第 162–163 行。**

- **具体场景**：第 8 轮的 checkpoint 被用于后续 warm start，但不是当前最新或最优，清理时被删除；第 7 阶段又承诺交付“每轮 commit 历史 + 检查点”。磁盘不足时究竟保哪些检查点、是否允许降级交付，没有约定。
- **修改要求**：区分代码快照、训练权重、续训状态和审计记录；用引用关系保护 BASE、最终候选、实验依赖和人工固定的产物。先完成归档与校验，再允许删除远端副本；只剩受保护产物仍无空间时暂停接单。说明代码包包含哪些轮次的权重，未保留的内容如何重新生成。
- **复现补项**：“commit + 环境 + 配置 + 日志”还应关联数据/划分版本、seed、预训练权重来源、实际执行命令、硬件与数值精度。导入本地 Git 仓库须明确未提交和未跟踪文件如何进入基线快照；Git LFS、子模块、外部链接也需检查。定义 round 与修复 attempt 的关系，避免“一轮一个 commit”把失败补丁历史覆盖掉。

### A07｜[6] 没有批实验完成标准，部分失败可能被包装成完整报告

**角度：产品完整性、科研严谨性。定位：D23/D26/D28；[6] 第 114–117 行；[7] 第 120–122 行。**

- **具体场景**：5 个 seed 仅 3 个成功，系统直接对成功项求均值；消融矩阵的一项持续 OOM，热力图将缺失结果填成 0；远端训练成功但结果回收失败，恢复时又重跑一次。当前 D23 的修复规则主要针对迭代阶段，没有说明在最终确认中是否还能自动改模型。
- **修改要求**：为批实验保存预期任务清单及逐项状态，定义全部完成、部分完成、失败和取消。结果缺失必须显式显示，不得补零或静默删去失败 seed；报告列计划/成功/失败数量及原因。区分重传产物与重跑训练，恢复只执行未完成项。确认阶段发生代码变化时必须创建新候选版本并使受影响的结果失效，不能将修复前后的运行混算成同一方法。

### A08｜后台定义了暂停与人工修订，UI 却没有把用户带回闭环的入口

**角度：产品完整性。定位：D11/D21/D23/D27；[3] 第 60 行；[5] 第 79 行；第 166–168 行；P1–P6，第 207–212 行。**

- **具体缺口**：P5 只有紧急停止，没有暂停原因、继续、终止、修订计划、重试失败任务或回滚后继续的操作；环境安装失败和指标不可得也没有承接页面。D11 的供应商配置、凭据状态和成本预算缺少 UI 落点。
- **修改要求**：不必增加大量页面，可在现有项目页补充统一状态面板：当前阻塞原因、受影响任务、允许操作、操作后从何处恢复。把“继续同一 run”“从 checkpoint 恢复”“新建一次尝试”“从旧候选继续搜索”明确区分。项目配置中补供应商/模型/预算与连通性测试，并明确断线或暂停的可见提示。UI 操作权限仍可保持单用户定位，不要求引入多用户账号体系。

### A09｜“想法查重”缺少检索边界，容易把未检索到误报为创新性成立

**角度：产品完整性、科研严谨性。定位：D4/D17/D22；[1] 第 41、44 行；[3] 第 56–58 行。**

- **具体场景**：用户只导入一篇 BASE 论文，系统据此输出“未发现相似工作”；表格提取把不同数据集的结果拼在一起；仅有摘要却生成了完整方法对照。需求写了文献对照与查重，没有定义是否外部检索、检索覆盖范围以及结论证据要求。
- **修改要求**：区分“在已导入文献中对照”和“外部相关工作检索”，记录来源、查询、检索时间与覆盖限制。方法/指标结论链接到原文页码、表格或可核验片段；解析不完整时降低结论确定性并提示补充。论文指标同时保留数据集版本、划分、评估协议、预训练与训练条件，不能只抽出一个最高分放进基线表。

### A10｜里程碑没有覆盖跨服务器验收，M2 的自动执行先于 M3 的人工定稿闸门

**角度：产品完整性、内部一致性。定位：D15/D16/D21；第 185–189 行；第 216–221 行。**

- **具体缺口**：M1 是单机纵切，M2 自动闭环，M3 才实现评审定稿；如果 M2 直接按默认值运行，就绕过 D21。多服务器调度、数据分发、4090 双卡并发和异构环境是正式需求，却没有明确验收里程碑。
- **修改要求**：不必机械调整开发顺序，但 M2 必须已有可人工审阅并显式确认的最小 experiment_plan，M3 再完善对话体验。给跨机任务分配、数据版本校验、并发目录隔离、断线对账、远端停机和预算耗尽分别指定里程碑与验收案例；否则单机自动再训成功不能代表产品闭环已完成。

### A11｜跨机环境只搭好一部分、或卡池运行中变化时，项目没有明确就绪规则

**角度：产品完整性、自动化流程漏洞。定位：D12/D15/D16/D20；[0] 第 31–38 行；[2] 第 48–51 行；P2 第 208 行。**

- **具体场景**：A 的环境和数据均已就绪，B 安装失败；用户再次点击搭建环境，系统应只修复 B 还是重建全部？训练配置新增一台服务器后，是否可以立即取任务？移除正在执行任务的 GPU 或修改服务器凭据，又该如何处理在途任务？正文要求涉及的每台服务器完成搭建，未给部分成功和运行中变更的策略。
- **修改要求**：维护机器在该项目、该环境/数据版本下的就绪状态，明确“全池就绪后启动”或“按预先允许的可用子池降级启动”。重复搭建只处理失败或失效步骤，不影响已运行任务；新增机器完成代码、环境、数据与冒烟校验后才能接单。移除卡采用停止派发并等待在途任务结束，或按明确取消操作处理；凭据变更后重新验证连接，并保留失联任务记录，不能通过删除服务器记录来假定训练已停止。

## 三、可选

### O01｜对接近的候选增加小规模复核，降低单 seed 过早淘汰好方案的概率

**角度：科研严谨性、产品效率。定位：D9/D26；[4] 第 72 行；[6] 第 117 行。**

单 seed 主循环可以保留。对接近历史最好、差距小于预设复核阈值的候选，可在验证集上追加少量预先登记的 seed，再决定是否晋级；也可保存少数候选用于预算内的统一验证复核。复核策略须事先约定且计入预算，不使用测试集挑候选，不自动变成“不断追加运行直到显著”。这是筛选质量增强，不替代 S06 的最终公平比较。

### O02｜按研究主张增加容量或计算量匹配的对照

**角度：科研严谨性。定位：[3] 第 58–59 行；[6] 第 116 行。**

如果主张是“模块设计更有效”，而新模块明显增加参数或计算，可增加参数量/计算量接近的普通模块或加宽 BASE 对照，检验收益是否主要来自容量增加。若主张“更高效”，则需要同硬件下的吞吐、时延或显存证据。不是每个项目都要穷举所有对照，应在定稿时将主张与必要证据关联；一旦某对照是核心主张成立的必要条件，就应升为该项目必做项。

### O03｜在链式血缘上补充假设与证据索引，减少重复尝试

**角度：产品效率、自动化流程。定位：D10/D25；[4] 第 69、73 行。**

“前几轮结论摘要”可能漏掉早期失败经验，LLM 后续又提出同样改法。可给每次改动关联假设、模块身份、验证结果、失败原因和适用条件，按需检索历史证据。暂不必把串行主循环改成复杂分支搜索；先让回滚后的新尝试能找到旧证据，并区分“同一思路重复失败”与“条件已改变，值得复试”。

## 四、D1–D28 内部一致性逐项核对

本表区分四种情况：**明确冲突**、**执行语义未闭合**、**遗漏落点**、**已明确修订或未发现直接冲突**。“未发现直接冲突”不代表设计已经完整；关联问题仍须处理。

|---|---|---|
| D1 单用户、无账号 | 未发现直接冲突 | 与第 5 行一致；不要求增加多用户系统，但单用户不等于执行代码可访问所有资产，见 S02。 |
| D2 独立 Web UI | 未发现直接冲突 | P1–P6 符合形态；人工恢复、配置和异常状态入口遗漏，见 A08。 |

| D4 论文参与设计 | 执行语义未闭合 | [1]/[3] 有解析和对照，但“查重”的检索范围及证据要求未定义，见 A09。 |

## 五、将关键问题转成可验收场景

以下用于把前述意见落实为需求验收，不新增问题数量，也不要求立即采用某个特定技术栈。

| 场景 | 必须观察到的行为 | 对应问题 |
|---|---|---|
| LLM 把验证脚本的得分乘以 100，训练仍正常结束 | 产品正式评分口径不变；篡改日志不能成为“模型提升”的证据，不能触发目标达成。 | S01 |
| 生成的代码尝试写 BASE 原目录或数据主副本 | 操作被运行权限阻止；原资产内容不变；失败被准确归类且有审计记录。 | S02 |
| 服务器已启动训练，但启动回执丢失；随后主服务重启 | 对账后识别已有 run，不重复派发；结果只入库一次。 | S03 |
| 搜索用尽总预算，或用户点击取消 | 不再启动消融、多 seed 或新一轮修复；远端执行停止约束。失联时显示“停止待确认”，不能虚报已停止。 | S03/S04 |
| 两张 4090 同时执行不同消融；其中一项需要新依赖 | 两项实际代码、配置和环境各自匹配登记版本，互不覆盖；新增依赖不改变正在运行任务。 | S11 |
| 数据同步中断，或两台机器同路径的标签内容不同 | 未校验通过的数据版本不能取得可调度状态；不得以“目录存在”放行训练。 | S10 |
| 最好模型出现在第 8 轮，第 12 轮终止，最终确认未超过 BASE | 按预定验证规则选择第 8 轮候选；如实报告确认未通过，不根据测试结果改选其他轮次或 seed。 | S06/S08 |
