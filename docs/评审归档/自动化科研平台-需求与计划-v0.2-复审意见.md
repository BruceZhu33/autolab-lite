本轮发现 **6 项严重、6 项建议**。严重项主要是已采纳规则之间的执行衔接，以及上一轮补充意见没有完整并入正文；并不是要求推翻现有方案或引入新一轮功能扩张。后置的 O01–O03 维持后置，本次不要求提前实现。

## 一、严重：仍需关闭的 6 个问题

### R01｜可信评测已定义，但每轮决策仍缺少明确的可信指标入口

**定位：第 70–75、123、165、170、252 行；D24/D29。承接旧 S01。**

- **已改进**：D29 明确产品侧受保护执行器，验收也要求篡改评分不能触发目标达成。
- **剩余问题**：[4] 仍是“拉取日志与指标 → 有效结果入库 → 终止判定”；D24 仍允许仓库生成的 JSON/CSV 或日志正则成为指标来源。“有效”是否指已由 D29 执行器核验，没有定义。可信执行器的详细描述又放在 [6]，实现者可能只在最终测试时启用它。
- **触发场景**：仓库将验证 Dice 从 0.80 打印成 0.99。最终测试执行器保持正确，但搜索已经依据日志达到目标而停止，或将错误轮次选为验证最佳候选。第 252 行的验收目标因而不能由当前数据流自然保证。
- **最小修改**：明确 D29 同时覆盖迭代期的验证评分与最终测试评分。用于终止、跨轮比较、候选选择的指标必须附带 run、数据版本、评测协议版本和可信评测来源；日志解析值可用于诊断，但未经验证不得进入正式判定。可保留文件/正则适配，但要明确其适用字段与可信结果的生产者。
- **验收补充**：篡改训练日志指标时，跨轮排名和终止结果均保持不变，而不仅是最后的测试分数不变。

### R02｜“GPU 硬预算”仍只落在轮间检查，断线或长任务期间没有执行责任人

**定位：第 71、75、85–86、172–173、189、192、255 行；D31/D32。承接旧 S03/S04。**

- **已改进**：预算强制、全程计费、取消后不再启动评估及远端停止回执，均已写清。
- **剩余问题**：明确列出的预算检查点是本轮结束和派发前；第 192 行又保证主服务重启时远端训练不中断。尚未要求远端在主服务离线时独立执行剩余预算/超时，也未约定并行任务怎样共同占用一个项目的剩余额度。
- **触发场景**：剩余 1 GPU·小时，同时启动三个一小时任务，每个都通过“尚有余额”检查；或主服务离线后，单个训练卡住数十小时。唯一 run ID 和重连对账能防重复派发，却不能阻止持续超支。
- **最小修改**：任务准入时原子预留额度或分配可执行时长，所有活跃任务的授权总额不得超过项目余额；远端 agent 独立执行截止时间/额度，断线不得获得额外额度。明确取消与派发的先后序列，已取消项目的旧回调不得再次发任务；声明计时口径、终止宽限及允许的计量误差。无需指定某个分布式框架，但必须明确控制责任与失联策略。
- **验收补充**：控制端失联且三卡并行时，依然满足约定的项目预算上限；显示“停止待确认”不能替代远端预算执行。

### R03｜已解决“数据副本一致”，仍遗漏“数据划分本身有效”

**定位：第 54、63、123、180、257 行；D29/D39。承接旧 S01 的二次复核补充。**

- **已改进**：校验和、原子发布、不可变副本与逻辑路径映射足以解决多机版本一致性问题。
- **剩余问题**：这些机制会忠实复制一份存在泄漏的划分。上一轮明确提出的对象/分组独立性与预处理拟合范围，在本版正文及验收表中没有落地；“测试集与训练数据隔离”尚未说明隔离的单位。
- **触发场景**：同一患者的不同切片、同一视频的相邻帧分别进入训练和测试，文件内容均不同，所有哈希校验照样通过；或归一化/特征选择先在全部数据上拟合，再划分。
- **最小修改**：在 plan 中登记按研究问题确定的独立单位、分组/时间规则和划分清单；校验不应跨集合的对象是否交叉。常规归纳学习下，需要拟合的预处理仅用训练部分学习；例外协议单独声明。将该检查放在协议冻结/基线验收之前，而不是复制完成后仅查文件存在。
- **验收补充**：不同文件名、不同哈希，但所属同一对象的记录跨集合时，系统按协议发现交叉；预处理拟合数据来源可追溯。预处理泄漏的原则及实例见 [scikit-learn 官方文档](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)。

### R04｜D34 用“确认优于 BASE”触发补跑 BASE，初筛与最终确认发生了循环定义

**定位：第 124–127、175、258、273 行；D34/D37。承接旧 S06。**

- **可以保留的取舍**：先给候选跑多 seed，BASE 暂跑一个 seed，仅对值得继续的候选补齐对照，是明确的节省预算策略。本次不要求无条件提前跑完全部 BASE seed。
- **剩余问题**：“候选确认优于 BASE 后再补齐 BASE”没有定义初筛指标、阈值和数据集；正式确认所需的 BASE 随机性数据尚未齐备，就先用了“确认优于”的结论。同时，没有写明补齐后必须重算最终差异并允许推翻初筛结果。
- **触发场景**：BASE 唯一 seed 是 0.80，候选均值 0.81，初筛通过；补齐后 BASE 均值变成 0.82。若状态已标为确认成功，报告与补跑结果会矛盾。反过来，单个 BASE seed 偏高导致初筛未过，也不能据此得出候选方法已被证明更差。
- **最小修改**：明确两个门槛：“初筛通过，值得补跑”与“全部指定对照完成后的最终确认”。建议按预登记的验证指标与阈值初筛；候选、协议、seed 列表和最终实验集合冻结后，再进行测试确认。补齐 BASE 与必要消融后重新聚合全部结果，最终允许确认失败。初筛停止应报告“未通过预算内筛选/未完成充分确认”，不得发布确定性的优劣结论。若选择以测试数据安排后续实验，需预先冻结整个分阶段协议并说明其分析限制，不能借测试反馈重新搜索模型。
- **可直接替换第 127 行的核心表述**：“候选多 seed 与 BASE 单 seed 的结果只用于预登记的初筛；初筛通过后补齐 BASE 与必要消融的同组 seed，全部指定结果到齐后才作最终比较与结论，初筛结论可被推翻。”

### R05｜计划版本已隔离，但协议修改后的基线、候选和权重迁移规则仍没接通

**定位：第 64、68、74、123–124、179 行；D29/D33/D35/D37/D38。承接旧 S09。**

- **已改进**：run 绑定不可变版本，旧结果不跨版本合并，D29 也明确协议变更需重建对照。
- **剩余问题**：D38 只说协议变更对新轮次生效，未把 D29 的“重建对照”接回 Round 0 验收；D37 的“历史验证最佳”也未明确限于同一可比协议。代码/权重是否能随旧队列和当前搜索状态延续，尚未规定。
- **触发场景**：数据划分修改后，候选继续从旧父权重续训；新测试集中的样本曾经属于旧训练集。即使结果按 plan_version 分表保存，新测试也已被旧权重接触。另一种情况是新指标下继续引用旧指标的 BASE 或历史最佳。
- **最小修改**：给协议变更定义转移规则：使受影响的基线、候选排序与消融结果失效，进入新的对照验收；旧任务可完成归档或明确取消，但不能成为新协议的默认比较对象。对数据划分变化检查继承权重的训练数据来源，必要时回到合规初始化重新训练。预算等纯控制变更不必触发整套重跑，应与科研协议变化区分。
- **验收补充**：更换划分后，曾训练过新测试样本的 checkpoint 不得作为新协议下未经披露的初始化；新协议的“最佳候选”只能在有效可比结果中选。

### R06｜最终确认中修复模型后，仍可能只补失败任务并混合新旧代码结果

**定位：第 76–78、124、128、164、182 行；D23/D37/D40/D41。承接旧 A07。**

- **已改进**：批实验清单、缺失值、失败数量和恢复时只补未完成项，均已明确。
- **剩余问题**：上一轮 A07 中“确认阶段改代码须生成新候选并使相关结果失效”没有并入。D41 的模型错误自动修复与 [6] 的“只补未完成项”结合，仍可能把不同模型归为同一批实验。每 run 的不可变快照只能证明各自跑了什么，不能保证汇总时方法相同。
- **触发场景**：seed 1、2 用 commit X 成功，seed 3 出错后修改了 forward 或 loss，重试用 X' 成功；系统按清单完成三项后输出三 seed 均值。
- **最小修改**：批实验绑定候选、协议、训练配方、初始化规则与矩阵版本；确认期间不得通过模型修复悄悄改变候选。若方法或训练语义改变，生成新候选并作废受影响的已完成对照，按新的确认清单重新执行。基础设施重试、产物重传可复用同一候选，不必因此全量重跑；是否影响结果语义需要明确判据。
- **验收补充**：seed 3 修复导致模型变化时，不能将 X 与 X' 汇总成同一方法的三 seed 结果。

## 二、建议：补清 6 处执行语义与文本同步

### R07｜消融阶段新增了人工确认，但产品仍承诺“定稿是最后一道人工闸门”

**定位：第 13–15、63、126、149、177 行；D8/D21/D36。关联旧 S07。**

第 126 行明确“重新生成，用户确认后冻结”，第 63 行仍称定稿为最后一道人工闸门，D8 也仍为定稿后全自动。新增确认可以是合理取舍，但应同步改写承诺。建议明确：原矩阵仍有效时自动进入确认；结构演化导致矩阵需修订时，进入“待消融方案确认”状态，经用户确认后继续。若本版意图是每次都确认，则直接注明该固定闸门。P5 也需显示这一暂停原因，不能让用户以为自动流程卡死。

### R08｜plan 字段与 LLM 上下文已补齐，但首次落实用户模块仍没有验收步骤

**定位：第 57–63、68–75、166 行；D21/D22/D25。关联旧 A01。**

在上下文中提供已定稿模块，不等于执行流程明确要求实现它们。当前仍是 Round 0 后由 LLM 自由判断下一步，没有“已批准方案落成 Round 1”的完成条件。补一句即可：“Round 0 验收后，先实现定稿方案并核对模块清单，再进入 Round 1；如发现方案不可实现或需改变核心假设，转入已定义的方案修订流程。”这不会阻止之后的结构级自治，只保证平台实际启动的是用户批准的研究。

### R10｜基线“配置合理”已要求，但公平训练配方仍只存在于字段名中

**定位：第 63、68、74、132、174、176 行；D33/D35。关联旧 S05/S12/A03。**

plan 里写了“基线与公平比较口径”，D33 却主要描述基线能正常运行，没有定义后续改动训练配方时的处理。例如 BASE 100 epoch、候选 300 epoch，或新增增强、预训练数据，仍可能满足统一初始化与基线验收。

建议明确比较协议至少承接训练预算口径、预训练来源、优化与增强设置、精度模式、模型选择规则；允许变化，但必须披露，并在结构收益主张需要时补采用相同训练配方的 BASE。父权重续训记录累计训练步数、优化器/调度器状态，避免只记录权重文件。效率指标按硬件分组是必要改进，但同型号内的 batch、输入规模和计时方式也要统一。这里不要求所有项目采用同一种公平性口径，也不要求把已后置的容量匹配对照全部前移。

### R11｜机器就绪状态补了，项目能否在可用子池上启动仍需一句明确规则

**定位：第 38、51–54、67 行。关联旧 A11。**

如果 A 已就绪、B 安装失败，第 38 行可以得知如何修复 B，却仍不能判断整个项目应等待还是先用 A。建议在项目计划中声明“要求全池就绪”或“允许按满足同一实验协议的可用子池运行”；后者仍须满足任务硬件约束及正式效率评测要求。另将“移除有在途任务的卡时……按显式取消处理”明确为删除操作的具体效果：立即取消在途任务，还是仅排空后移除。文档可选定一种默认策略，不必新增复杂调度功能。

### R12｜停机与预算的可靠性验收全部放到 M4，晚于 M2 的自动闭环使用

**定位：第 211、213 行。关联旧 A10。**

M2 的人工定稿闸门已修复，这是本轮可以确认的改进。但断线对账、远端停机、预算耗尽不启动评估被统一放到 M4；如果 M2 将作为无人值守可用版本，这些基础保护就验收得太晚。

建议 M2 至少验收单机下的取消竞态、运行中预算/超时、断线对账和失败重试；M4 再完成多机并发额度、双卡隔离和完整科研产物验收。若 M2 仅是人工看护的开发演示，应在里程碑注明该限制，不能同时把它视为无人值守版本。
